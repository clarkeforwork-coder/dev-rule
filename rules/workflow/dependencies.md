# 第三方套件與依賴管理

<a id="dependency-evaluation"></a>
## 引入前的評估

1. **採用理由**。先確認標準函式庫、既有框架與已採用的套件能否滿足需求，再依影響範圍說明新增依賴的具體收益與維護成本。
2. **套件身分**。核對完整套件識別（含命名空間）、發布者與發布來源，只從專案核准的來源取得。無法確認身分時，須暫緩引入。
3. **維護狀態**。依用途、影響範圍與替換成本，評估維護者對缺陷的回應及對執行環境的支援。關鍵依賴須確認安全通報管道，以及停止維護時可行的因應方式。
4. **授權條款**。確認條款符合預定用途與交付方式，並能履行相關義務。隨產品交付的間接依賴也須納入檢查。授權不明或相容性未確認時，暫緩採用並交由指定負責人釐清。

<a id="build-changes"></a>
## 建置與變更

5. **版本鎖定**。可部署產物須鎖定直接與間接依賴的實際版本。CI 與發布建置依同一份鎖定檔或等效紀錄執行。宣告與鎖定紀錄不一致時須停止建置，經審查與驗證後再更新。供其他專案引用的函式庫須明訂支援的版本範圍，並保留可重現的測試版本組合。
6. **產物完整性**。安裝與建置須以套件管理工具或等效機制驗證取得的內容。即使版本號相同，內容與可信紀錄不符時仍須停止使用並釐清差異。更新驗證依據須經審查。
7. **變更範圍**。新增或升級套件時，須檢視直接與間接依賴實際新增、移除或升級的項目，依交付範圍與執行時機決定審查深度。安裝或建置時新增或變更的自動執行行為須明確確認，包括僅在測試或 CI 使用的套件。

<a id="vulnerabilities-upgrades"></a>
## 漏洞與升級

8. **漏洞判定**。依實際版本、使用方式、暴露範圍與可能後果判定優先順序，指定負責人及處理期限。判定不受影響時須保留可核對的依據，例如建置與執行環境均未啟用受影響功能。
9. **暫無修補**。須針對漏洞的觸發條件驗證暫時措施，並記錄剩餘風險。若仍須承擔風險才能繼續使用，須由專案負責人核准適用範圍與期限。修補可用、使用條件改變或期限屆滿時須重新評估。[例外核准](rule-governance.md#例外核准)

<a id="maintenance-removal-traceability"></a>
## 維護、移除與追溯

11. **維護責任**。每項直接依賴須能對應到負責團隊，並依重要性訂定檢視時機。支援終止、發布權移轉或相容條件改變時，須重新評估並明訂處置。
12. **直接依賴宣告**。專案或模組須在自己的依賴清單中宣告直接使用的套件，標示執行、建置或測試等用途，不得依靠其他套件間接帶入。
13. **移除依賴**。確認執行、建置與測試流程均已停止使用，包括透過設定載入的外掛，再移除直接依賴並同步更新依賴紀錄。移除後須在乾淨環境重新安裝並驗證受影響的流程。
14. **發布追溯**。每個發布產物須能追溯到實際隨附的直接與間接依賴版本，以便收到漏洞或撤回通知時核對受影響的發布範圍。紀錄形式由專案決定。
15. **自行修補**。記錄上游基準版本、修補內容與維護責任，使發布產物可追溯到實際使用的修補版本。須明訂重新評估或移除補丁的條件，例如上游納入修正且原缺陷案例驗證通過。

<a id="sources-build-security"></a>
## 來源限制與建置安全

16. **疑似竄改**。有具體跡象時，須暫停使用可疑版本，依其執行權限與使用紀錄追查受影響的建置、憑據與發布產物。即使套件僅執行過安裝腳本，也須納入追查。確認套件版本與建置環境可信後，才能恢復受影響的發布流程。
17. **多個套件來源**。須明訂套件識別與來源的對應，開發、CI 與發布建置遵守相同解析規則。內部或限定來源的套件無法從指定來源取得時，須停止安裝，不得改用其他來源的同名套件。
18. **腳本權限**。第三方套件的安裝與建置腳本須以該步驟所需的最小權限執行，依用途限制檔案、網路與憑據存取。例如只有發布步驟需要發布權杖時，安裝腳本不得取得該權杖。[安全共通規範](../quality/security.md#授權與資料範圍)

審查與驗收方式見[依賴管理驗收](#acceptance)。

<a id="acceptance"></a>
## 驗收

驗收案例的選擇與維護依[驗收共同原則](../quality/testing.md#acceptance-principles)。

<a id="upgrade-acceptance"></a>
### 升級驗收

10. **升級驗收**。依實際用途與變更風險驗證受影響的行為及相容性。例如升級付款流程使用的 HTTP 用戶端時，須核對逾時後的重試行為。安全修補須核對最終使用的產物，確認修補已生效。

<a id="dependency-management-acceptance"></a>
<a id="依賴管理驗收"></a>
### 依賴管理驗收

依[第三方套件與依賴管理](../workflow/dependencies.md#引入前的評估)，按變更類型核對下列結果。

- 引入或升級時，比對依賴宣告與實際解析差異。核對新套件的來源、用途、授權義務、維護責任，以及腳本可取得的權限。以專案實際使用的功能驗證受影響行為。
- 核對 CI 與發布建置使用同一份鎖定紀錄。驗證內容不符時會停止使用，限定來源缺少指定版本時也會停止安裝。移除依賴後，在乾淨環境驗證相關流程，包含透過設定載入的外掛。
- 從指定發布版本查回產物實際隨附的依賴與補丁，核對安全修補是否進入該產物。疑似竄改時，另查建置期間曾執行的腳本與當時可存取的憑據，確認恢復發布的條件已成立。
- 對仍未修補的漏洞，核對影響判定、負責人與期限。若採暫時措施，須逐一核對可觸發漏洞的入口，驗證措施的實際涵蓋範圍，並核對剩餘風險的例外核准範圍與有效期。

- 共用函式庫須核對支援範圍與可重現的測試版本組合。檢視維護狀態或自行修補版本時，確認重新評估、替換或移除補丁的條件及負責人。
