# Git、PR 與程式碼審查

## 提出變更與審查

1. **PR 範圍**。每個 PR 須有明確且可驗證的目的，相關實作與測試一併審查，無關變更分開。拆分後的每個 PR 都須符合專案約定的可建置、可測試與相容條件。未完成的功能須有明確啟用限制。範圍依關聯性決定，不訂固定檔案數或行數上限。
2. **PR 說明**。說明變更目的、主要行為差異與影響範圍，提供實際驗證結果，並揭露尚未驗證的部分及必要的相容、設定或遷移安排。詳細程度依風險調整。
3. **審查責任**。專案須依風險明訂審查資格、人數與核准條件。涉及特定業務或技術責任的變更，須由具備相應判斷能力的責任人參與。例如公開契約變更須涵蓋使用端相容性的判斷。
4. **審查意見**。區分合併前必須處理的問題與改善建議，說明風險、契約或既定規範等依據。阻擋合併的問題須完成修正、釐清或取得有效例外核准。歧見由專案指定責任人裁決並記錄理由。[例外核准](rule-governance.md#例外核准)

## 合併條件與分支保護

5. **核准後修改**。新增修改須說明影響範圍，補做受影響的驗證，並由相關審查者重新確認會影響原核准結論的部分。合併時須確認核准及檢查結果仍適用於實際合併內容。輕微變更的處理方式由專案明訂。
6. **必要檢查**。專案須明訂必要檢查與適用條件。必要檢查失敗、仍在執行或應執行卻未執行時，不得直接合併。須完成處理，或依既定例外流程核准並留下驗證依據。
7. **整合驗證**。合併前須確認與目標分支整合後仍符合契約及必要檢查。依變更交互影響驗證整合結果，衝突處理若影響行為，須補做相應驗證與審查。具體整合驗證機制由專案決定。
8. **分支保護**。共同開發與發布分支須在版本庫平台設定明確的寫入保護，人工及自動化操作都須遵守合併條件。繞過保護須經例外核准，保留操作者、原因及實際變更等可追溯紀錄。
9. **歷史改寫**。專案須明訂允許整理提交或 rebase 的分支。已分享分支改寫前須協調，更新遠端前須確認其版本未出現未處理的變更。若已有新提交，停止更新並重新核對，保留他人成果。
10. **提交追溯**。合併後的提交紀錄須清楚表達變更目的，並能追溯對應的 PR、審查與驗證依據。若有需求單或架構決策，須保留對應關係。提交格式與合併方式由專案統一。

## 回退、跨分支與緊急處理

11. **回退或追加修正**。回退前須評估後續依賴，以及資料、設定與契約相容性。回退或追加修正都須保留原因及原變更的關聯，並完成適用的審查與驗證。緊急處理依既有例外流程執行。
12. **跨維護分支修正**。明訂受影響且仍在支援的分支與負責人，逐一追蹤套用及驗證結果。即使可直接 cherry-pick，也須依各分支實際程式與依賴驗證行為，並保留各筆修正與原問題的關聯。
13. **緊急變更補驗**。經核准延後部分審查或驗證時，須明訂待補項目、負責人與期限，追蹤至完成。後續發現問題時須依影響採取修正、回退或其他處置，並將驗證與處理結果連回原 PR。

## 作者與驗證責任

14. **作者自查**。提出正式審查前，作者須檢視實際差異，確認內容符合 PR 目的、相關測試與文件已同步，並完成適用的驗證。未完成的檢查須揭露原因及待確認事項。
15. **測試有效性**。審查須對照預期行為，確認測試輸入、斷言與失敗情境能支持變更目的。可穩定重現的缺陷須保留能在修正前暴露問題、修正後通過的回歸案例。[共通測試策略](../quality/testing.md)
16. **AI 與工具產生內容**。PR 提出者須理解提交內容的目的、主要行為與風險，並對內容及驗證依據負責。AI 或工具產生的變更同樣適用審查與合併要求。工具宣稱驗證通過時，須核對實際執行結果及對應版本。產生器輸出的修改方式依[工具產生碼](rule-governance.md#工具產生碼)。

合併流程的核對方式見[Git 與 PR 驗收](../quality/rule-verification.md#git-與-pr-驗收)。
