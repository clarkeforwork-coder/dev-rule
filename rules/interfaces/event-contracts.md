# 事件命名與內容設計

<a id="naming-and-publication"></a>
## 名稱、粒度與發布條件

業務事件使用一致的領域詞彙描述已成立的事實。命令則表達要執行的動作。專案統一命名語言與大小寫，例如：

| 名稱 | 契約語意 |
| --- | --- |
| `CancelOrder` | 命令，要求取消訂單，可能遭拒絕。 |
| `OrderCancellationRequested` | 已提出取消申請，消費方只能據此判斷申請已提出。 |
| `OrderCancelled` | 訂單已取消，消費方可依取消完成的事實處理。 |

使用端需要辨識的不同事實應分別命名。同一事實若只有原因或發起者不同，且業務效果相同，則用欄位區分。概括事件也須限定承諾範圍。例如 `OrderUpdated` 若只通知使用端重新查詢，消費方不得據此釋放庫存。

各事件須定義何時構成一次新事實，以及重複操作是否符合發布條件。API、後台與背景工作均依同一條件判定。例如「收件地址已變更」須在地址確實改變時才成立。再次提交相同地址不構成第二次地址變更。

<a id="ownership-and-publication-scope"></a>
## 責任歸屬與公開範圍

- 由管理該業務狀態的模組確認事實並負責事件語意。背景元件可代送，須保留原來源與事件 ID。下游模組確認自己負責的新事實時，使用自己的來源與新的事件 ID。
- 發布方須標示開放跨模組或跨服務訂閱的事件。消費方只能依賴公開契約承諾的發布條件、欄位與語意。內部事件可沿用原格式公開，發布方自此承擔相容性責任。

<a id="payload-and-field-combinations"></a>
## 內容與欄位組合

事件僅攜帶契約用途需要且訂閱者有權接收的資料。若用途是刷新畫面，提供業務對象 ID 供查詢目前狀態即可。若用途是還原某次地址變更，契約須提供當時的前後值，或提供可取得該歷史版本的參照。

契約須明訂條件式必填、合法欄位組合與缺值語意，使接收端能依事件及契約驗證。例如人工取消若必須說明原因，就應能辨識「人工取消且原因缺漏」的錯誤。無效事件依既有驗證與隔離流程處理。欄位組合若表達不同業務事實，應重新檢視事件粒度。

<a id="metadata"></a>
## 中繼資料

同類事件統一中繼資料與業務欄位的用途及位置。標頭、共用外層與業務內容的具體格式由專案選擇。轉送、保存與重播須保留解讀及去重所需的中繼資料。若協定要求同一資訊存於兩處，契約須指定主要來源與不一致時的處理方式。

| 資訊 | 契約要求 |
| --- | --- |
| 事件 ID | 識別一次事實，明訂唯一性範圍。重送與重播沿用原值。 |
| 業務對象 ID | 識別事實涉及的對象。同一對象可發生多次事件，不得單憑對象 ID 去重。 |
| 流程 ID | 需要跨步驟追蹤時才納入。同一流程中的多個命令與事件可共用。 |
| 時間 | 定義欄位代表的時點、記錄者、時區與精度。重送與重播保留原始發生時間。衡量發布延遲或追查傳送時才需發布時間，每次傳送的時間另記。判斷先後依契約的版本或序號。 |
| 事件契約版本 | 用於選擇解讀格式及語意的規則。多版並存時，可透過事件類型、Schema 識別碼或版本欄位辨識。 |
| 業務對象版本 | 需要判斷對象狀態的新舊時，定義版本適用範圍。用它偵測缺漏時，須說明哪些變更推進版本、消費方是否應收到每次變更。兩種版本皆有需要時須分別識別。 |

<a id="history-and-corrections"></a>
## 歷史解讀與更正

契約變更須評估仍在消費或重播範圍內的舊事件。保留舊版解讀能力，或使用經驗證的轉換規則。補值須有舊契約或當時資料為依據。例如新增幣別欄位時，不能套用商戶今天的預設幣別。無法確認時應標示資料不足，依既定流程處理。一般變更原則見[資料契約](data-contracts.md#compatibility-and-changes)。

已發布內容有誤時，保留原事件，以新的事件 ID 發布更正，引用被更正的事件 ID，指出錯誤內容與正確值。後續真正發生的業務變化須另發對應事件，例如付款金額誤植需要更正，付款後實際退款則發布退款事件。契約須定義更正早於原事件到達、重複送達及整批重播時的處理，使最終結果一致並避免重複副作用。執行機制見[事件可靠性](events.md#replay-and-backfill)。

<a id="examples-and-verification"></a>
## 範例與驗證

每種公開事件至少提供一個有效的虛構範例，可依風險補上條件式缺值、更正或舊版重播的預期結果。發布方與消費方須引用同一份契約的主要定義來源，契約變更時同步更新範例與測試。雙方的驗收方式見[本文件驗收](#acceptance)。

<a id="acceptance"></a>
## 驗收

驗收案例的選擇與維護依[驗收共同原則](../quality/testing.md#acceptance-principles)。

<a id="public-event-contract-verification"></a>
<a id="公開事件的契約驗證"></a>
### 公開事件的契約驗證

每種公開事件至少有一個有效範例。發布方與消費方的測試須依事件命名與內容設計引用同一份契約，並分別驗證以下行為。

- 發布方驗證觸發條件與實際產出。例如先把地址從 A 改成 B，再提交一次 B，只有第一次成立「地址已變更」。驗證事件來源、識別、必要欄位組合，以及內容限於契約用途和訂閱者權限。
- 消費方驗證有效範例會產生契約預期的結果，條件式必填欄位缺漏時能依規定處理。測試資料使用虛構值。
- 依支援範圍與風險，以舊版範例驗證重播後的歷史語意，以原事件與更正事件驗證亂序、重複及完整重播的結果。傳送或代送後須仍可辨識原事實，避免重複副作用。
- 變更公開契約時，檢視發布方、消費方、範例及測試是否同步更新。訊息傳送與恢復的驗證另依[事件可靠性](../interfaces/events.md#acceptance)。
