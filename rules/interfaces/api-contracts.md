# API 操作語意與介面設計

本文件定義跨語言、跨協定的 API 設計要求，不強制 REST、CQRS 或查詢與修改分開部署。具體路徑、方法、函式名稱及傳輸格式由專案依協定統一選定。

<a id="queries-and-business-operations"></a>
## 查詢與業務操作

- API 必須明確區分查詢資料與改變業務狀態，查詢不得產生使用端未預期的業務變更。
- 查詢可產生必要日誌、指標或快取填入，但不得順便執行成立訂單、扣款或取消等隱藏業務操作。
- 優先表達使用端需要的業務能力，不直接以資料庫結構設計 API。
- 單純資料管理可使用新增、查詢、修改與刪除，不要求全部改為動作型 API。
- 涉及狀態轉換或業務規則時，提供明確操作，例如取消訂單，不允許使用端任意修改狀態以繞過規則。
- 不提供讓使用端任意指定資料表、欄位或更新條件的通用寫入入口。
- 操作粒度應能完成明確的業務目的，避免使用端自行串接底層修改來維持基本業務條件。
- API 契約與內部資料表隔離，資料庫重構不應無必要地改變對外介面；資料模型遵循[邊界物件](../architecture/boundary-objects.md#separation)。

<a id="consistent-conventions"></a>
## 統一慣例

- 同一專案必須統一 API 命名與操作表達方式，同類型操作遵循相同慣例，不由各模組自行選擇。
- 資源與動作使用一致的領域詞彙，避免同一概念出現不同名稱。
- 查詢、建立、更新、刪除與業務動作須有可辨識的命名與表達，並遵守所選協定語意，不為方便而混用。
- HTTP API、RPC 等可各有適合的慣例；不同形式並存時，必須定義適用範圍與理由，不臨時混搭。
- 偏離專案慣例須依[規範治理](../workflow/rule-governance.md#exception-approval)核准。

<a id="operation-scope-and-success"></a>
## 操作範圍與成功保證

- 每項操作必須說明對象、必要條件與業務效果。
- 成功結果須明確表示哪些變更已完成、哪些仍待後續處理，不讓使用端自行猜測。
- 多步驟操作明確定義本次完成範圍，不把尚未完成的後續工作算入成功。
- 已接受、處理中與已完成的區分遵循[外部整合可靠性](external-services.md#accepted-and-completed)，部分成功及結果未知遵循[錯誤處理](../coding/error-handling.md#partial-success)。
- 使用端只需依公開契約理解結果，不必了解內部分層、資料表或服務呼叫順序。
- 實作與文件必須一致，不得在未調整契約的情況下改變成功語意；變更須遵守[資料契約](data-contracts.md#compatibility-and-changes)的相容性要求。

<a id="update-semantics"></a>
## 更新語意

- 必須明確區分完整替換與部分修改。
- 完整替換須定義可替換的資料範圍及省略欄位的處理方式，不讓使用端修改系統管理欄位。
- 部分修改只修改明確提供的欄位，未提供者保留原值。
- 清空、空字串與預設值遵循[空值語意](../coding/nullability.md#null-state-semantics)，不由框架自行猜測。
- 狀態轉換或業務規則仍透過明確業務能力執行，不藉通用更新繞過。
- 更新若依賴使用端先前讀取的版本，契約須提供版本條件或其他衝突偵測方式；衝突時明確回報，不默默覆蓋。內部保障遵循[交易與併發控制](../data/transactions.md#concurrent-updates)。

<a id="delete-semantics"></a>
## 刪除語意

- 明確區分刪除、封存、停用與取消，不能因內部都使用狀態欄位就混用名稱。
- 說明操作後是否仍可查詢、是否可恢復，以及關聯資料或業務流程的影響。
- 有關聯資料或未完成流程時，定義拒絕、連帶處理或背景作業條件，不依賴資料庫預設行為決定。
- 對不存在或已刪除的對象，事先定義回應；重複請求不得重複產生非預期副作用。
- 非同步刪除尚未完成時，只能回報已接受或處理中，不提前宣稱完成。
- 軟刪除或實體刪除由專案決定，對外語意必須一致且可驗證。

<a id="absence-and-empty-results"></a>
## 不存在與無結果

- 單一對象不存在時，提供明確的不存在結果，不用空物件或預設資料假裝找到。
- 集合查詢沒有符合資料時，正常回傳空集合，不視為系統錯誤。
- 修改或執行業務操作時對象不存在，依契約處理，不默默建立新對象；需要不存在就建立的行為時，必須明確定義。
- 權限不足時是否揭露對象存在，由安全政策統一決定，避免透過回應探測他人資料；此對外揭露限制不影響內部保留正確判斷與診斷資訊。
- 具體回應格式與協定狀態由專案統一制定。

<a id="identity-and-managed-fields"></a>
## 身分與系統管理欄位

- 操作者身分、權限與所屬範圍以可信驗證結果為準，不直接相信請求欄位。
- 建立時間、審核狀態等系統管理欄位由伺服器依規則決定，不讓一般使用端任意指定。
- 使用端可提供操作對象 ID，但伺服器仍須驗證操作權限。
- 管理員代他人操作等需求須在契約明確表達，驗證代理權限，並區分實際操作者與被代理對象。
- 客戶端確實需要提供的時間或識別資訊，須區分用途，不與伺服器認定的事實混用。

<a id="wire-format-and-data-semantics"></a>
## 傳輸格式與資料語意

- 時間須區分時間點、當地日期與時間長度，必要時指定時區或偏移，不讓雙方猜測。
- 金額與數值須定義幣別、單位、精度及捨入規則。
- 識別碼須定義格式與比較方式；除非契約允許，使用端不得解析內部結構推斷業務資訊。
- 列舉與狀態使用穩定的機器可讀值，不以顯示文字判斷；新增值仍須評估相容性。
- 傳輸格式須保留必要精度與範圍，不能因使用端語言差異而截斷或失真。
- 具體格式由專案契約統一選定，內部仍遵循[專屬型別要求](../coding/domain-modeling.md#dedicated-types)。

<a id="entry-point-consistency"></a>
## 多入口一致性

- 同一業務能力由所屬模組統一執行，各 API 入口負責協定轉換與必要呈現調整，不各自複製業務規則。
- 可依使用端提供不同資料組合，不得因此略過授權、驗證或業務不變條件。
- 管理後台有特殊權限或不同操作效果時，必須明確定義為受控能力，不暗中繞過一般規則。
- 不同協定可以使用不同結果格式，但成功、失敗與完成程度的業務語意必須一致。

<a id="examples-and-contract-maintenance"></a>
## 範例與契約維護

- 公開操作必須提供正常使用方式與適用的重要失敗、邊界情境，包含必要輸入、預期輸出及操作效果，不只列欄位型別。
- 範例不得包含真實秘密或敏感資料。
- 範例與測試引用[資料契約](data-contracts.md#primary-contract-source)的主要定義來源，不另建獨立維護的契約。
- 契約或行為變更時，同步更新受影響的文件、範例與測試。
- 透過契約測試或整合測試確認實作一致；適用情境與驗收見[本文件驗收](#acceptance)。

列表操作的查詢參數與回應保證見[列表 API 的分頁、篩選與排序](list-queries.md#page-size-and-pagination)。變更既有操作的成功保證時，依[API 版本管理、淘汰與使用端遷移](api-versioning.md#version-selection-and-maintenance)評估相容性與切換方式。

### API 邊界的缺值轉換

API 須依實際協定明訂查無資料、欄位未提供、明確清空及空集合的語意。使用 HTTP／JSON 時，明訂 HTTP 狀態、欄位省略、JSON null 與空集合各自的適用情境，不將省略與 null 任意互換；其他協定採其適合的表示方式。內部缺值型別須在 API 邊界依公開契約轉換，不直接暴露語言的缺值包裝型別，也不得由框架預設序列化行為決定對外語意。內部非空要求與外部缺值表示分別遵循契約，不統一指定所有查無資料情境的協定狀態。具體語言與框架落實分別由其規範處理。

<a id="acceptance"></a>
## 驗收

驗收案例的選擇與維護依[驗收共同原則](../quality/testing.md#acceptance-principles)。

<a id="api-契約與操作驗證"></a>

依API 操作語意與介面設計，以契約測試或整合測試確認公開契約、範例與實際行為一致。

- 驗證正常操作的必要輸入、預期輸出與業務效果，不只確認欄位型別。
- 依操作風險與語意選擇重要情境，例如對象不存在、集合無結果、版本衝突、完整替換與部分修改、重複刪除及非同步完成程度。
- 確認查詢沒有隱藏業務副作用，更新與刪除不繞過業務條件，身分與管理欄位不受未授權輸入控制。
- 確認適用的傳輸格式保留必要精度與範圍，以及同一業務能力在不同入口維持一致的規則與結果語意。
- 不要求每個 API 套用全部情境；範例不得包含真實秘密或敏感資料。
- 範例與測試引用既有契約來源，不建立另一套獨立定義；變更時同步更新文件、範例與測試。
