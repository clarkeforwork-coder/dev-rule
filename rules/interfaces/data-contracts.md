# 資料契約

適用於對外 API、模組間公開資料，以及事件與訊息等契約。

API 的查詢與修改、成功保證、欄位及傳輸語意，依[API 操作語意與介面設計](api-contracts.md)制定；本文件管理共用的契約來源、相容性與對外錯誤要求。

## 主要定義來源

- 每個契約必須指定唯一主要定義來源；可由專案選擇 Schema／規格優先或程式碼優先，不強制所有專案使用同一形式。
- 其他形式優先由主要來源產生；無法產生時，必須以自動化檢查確保一致，不讓型別、驗證 Schema 與文件各自演進。
- 無論來源為何，均須遵守[資料驗證](../coding/validation.md)，靜態型別不能取代執行期驗證。

## 相容性與變更

- 變更前必須辨識使用端與影響，不得只確認提供端能編譯。
- 刪除欄位、改變型別、選填改必填或改變欄位語意，都必須評估為可能的破壞性變更。
- 新增欄位也不直接視為相容，必須考量必填要求及使用端是否拒絕未知欄位。
- 可同步更新的內部模組，應在同一次變更更新所有使用端並完成驗證。
- 無法同步更新的使用端，必須透過版本或過渡期維持相容，訂明遷移與停止支援方式。

API 的版本選擇、支援期與停用條件見[API 版本管理、淘汰與使用端遷移](api-versioning.md)。

## 對外錯誤契約

內部失敗分類、例外傳遞，以及降級、結果未知、部分成功與取消的處理依[錯誤處理](../coding/error-handling.md)執行；本節定義對外契約的表達與資訊揭露限制。

- 錯誤回應必須使用明確型別，定義穩定錯誤代碼，以及適用的訊息、欄位錯誤等資訊。
- 使用端依錯誤代碼判斷行為，不依賴解析可能改寫或翻譯的錯誤文字。
- 內部例外必須經邊界轉換後才對外回傳，不得直接輸出例外物件、堆疊、SQL 或第三方原始錯誤。
- 各種錯誤只攜帶適用資料，不將所有可能資訊塞進通用物件。
- 專案可依協定決定具體格式，但必須維持明確型別與資訊揭露限制。

以契約一致性檢查、使用端相容性驗證及錯誤回應測試確認要求；需要業務語意判斷的部分列入人工審查。例外依[規範治理](../workflow/rule-governance.md)處理。
