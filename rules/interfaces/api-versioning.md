# API 版本管理、淘汰與使用端遷移

<a id="new-version-criteria"></a>
## 何時提供新版

以既有使用端能否繼續依原契約運作判定相容性。除了輸入與輸出格式，還須檢查業務效果與成功保證。例如取消訂單的成功回應原本代表「已取消」，改成「已受理」即屬破壞性變更，即使欄位完全相同。

相容變更可在原版本發布。破壞性變更若影響無法同步升級的使用端，必須保留舊契約，並提供可明確選用的新版。內部 API 若能辨識所有使用端，可協調同次切換並驗證所有受影響操作。部署或回退期間只要仍可能出現舊使用端，就須維持相容。欄位變更的評估依據見[資料契約](data-contracts.md#compatibility-and-changes)。

<a id="version-selection-and-maintenance"></a>
## 選擇版本與並存維護

- 同一專案的同類 API 採一致的版本選擇方式。版本識別放在路徑、標頭或其他協定位置，由專案決定。
- 使用端指定版本時，伺服器依指定契約處理。未知或已停用的版本不得轉送至其他版本執行。使用端省略版本時，契約須明訂拒絕或採用哪個預設版本。發布新版不得讓依賴預設值的請求自動切換到不相容的行為。
- 每個受支援版本須公布維護範圍，包括是否新增功能、如何修正違反契約的缺陷、哪些版本接收安全修補，以及如何通知受影響的使用端。修正若改變使用端依賴的行為，須評估相容性。安全修補若涉及契約變更，須說明影響與遷移方式。
- 已宣告淘汰的版本可停止新增功能，但在公告的支援期內仍須履行原契約。共用業務元件變更時，須按各受影響版本的契約驗證行為。

<a id="deprecation-announcements"></a>
## 淘汰公告與通知

| 公告項目 | 必須說明的內容 |
| --- | --- |
| 影響範圍 | 列出版本及操作。若只移除部分能力，指明受影響的操作。 |
| 遷移路徑 | 指出替代版本或操作、行為差異與必要調整。功能直接終止時明示沒有替代方案。 |
| 時程 | 分列淘汰生效日與預定停止支援日。截止日待定時，公布下次更新時間。過渡期依使用端能否自主升級、發布週期及影響範圍決定。 |

已知使用端須主動通知維護團隊或整合窗口，並附遷移文件。關鍵使用端未回覆時，由 API 負責人追蹤確認。公開 API 須在固定且可查閱的管道保留公告，協定支援時可在舊版回應附淘汰提示與遷移連結。時程變更時，透過原管道更新停止支援日期。

<a id="migration-and-recovery"></a>
<a id="切換恢復與驗收"></a>
## 切換與恢復

- API 提供方說明版本差異及驗收情境。使用端負責人依實際使用的操作與風險驗證業務結果。關鍵流程須涵蓋適用的成功、失敗與處理中情境，正式切換後核對結果，才能標記為已遷移。
- 遷移計畫須說明哪些操作可以切回、切回期限，以及舊版如何讀取新版已寫入的資料並接續進行中的工作。例如已受理的扣款應追蹤原操作結果，不能在切回後再發起一次扣款。
- 明列不可逆步驟與向前修復方式，例如舊版無法處理新版訂單狀態時，由哪個流程接手。關鍵流程須在切換前用代表性資料驗證適用的恢復方案，並指定異常時決定切回或向前修復的負責人。

<a id="retirement-and-records"></a>
## 停用與紀錄留存

1. 不得早於公告的停止支援日期停用。下線前，API 負責人須確認關鍵使用端已在正式環境切換的證據，並列出尚未確認者。按版本與操作核對用量，觀察期間須涵蓋已知低頻工作，例如月底結帳。
2. 若仍有流量或未確認的關鍵使用端，由負責人記錄剩餘影響及延期或依公告停用的決策。公開 API 可依公告政策與可取得的用量資料評估，不要求逐一取得匿名使用端回覆。
3. 舊版識別不得重新指向不相容的新版。舊入口仍能接收請求時，須明確拒絕執行，回傳可辨識的停用錯誤及遷移文件連結。入口完整移除後，原公告管道仍須保留停用紀錄及遷移資訊。

版本相容性與遷移驗收的檢查項目見[本文件驗收](#acceptance)。

<a id="api-版本相容性與遷移驗收"></a>
### API 版本相容性與遷移驗收

依API 版本管理、淘汰與使用端遷移，將提供方的契約驗證與使用端的遷移驗收分開確認。

- 驗證明確指定與省略版本的請求均依契約處理。對未知版本或仍可接收請求的停用入口，確認回傳可辨識的錯誤，且未執行新版操作。
- 對共用實作或修補所影響的每個受支援版本，驗證輸入、輸出與可觀察的業務效果。例如舊版取消訂單承諾同步完成時，收到成功回應後應能查到已取消。新版若只承諾已受理，則須驗證使用端能追蹤最終結果。
- 關鍵流程在切換前以代表性資料驗證成功、失敗、處理中及適用的恢復路徑，涵蓋新版寫入的狀態與尚未完成的操作。正式切換後，由使用端負責人核對業務結果。
- 停用審查核對公告日期、關鍵使用端遷移紀錄及涵蓋低頻操作的實際用量。仍有使用或狀態未確認時，檢查負責人是否記錄影響與處置決策。
