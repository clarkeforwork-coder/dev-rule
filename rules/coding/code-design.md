# 程式碼設計與公開介面

## 函式責任與參數

依責任與變更原因決定是否拆分函式，保留清楚的流程入口。例如 `cancelOrder` 可協調取消與申請退款，但依付款方式計算退款金額的規則應由負責退款的元件維護。共通規範不訂固定行數上限。

參數必須讓讀者在呼叫處辨識操作意圖。多個布林值或相似參數容易混用時，可採具名參數、明確的選項型別，或拆成各自有意義的操作。有不合法的組合時，須以型別限制可表達的狀態。像 `setNotificationsEnabled(false)` 這類用途清楚的呼叫，可以保留布林參數。評估依據是意圖與組合是否合法，不訂固定參數數量上限。型別宣告遵循[型別安全](type-safety.md)。

## 可見性與狀態所有權

- 類別、函式與屬性依使用者採最小必要可見性。讀取與修改範圍分別決定，跨模組公開能力遵循[模組責任與公開入口](../architecture/module-boundaries.md)。
- 無須改變的資料預設不可變。可變狀態須有明確擁有者，並以維護業務規則的操作修改。例如公開 `cancel()` 檢查取消條件，將直接寫入訂單狀態的能力留在內部。
- 讀取入口不可洩漏內部集合或巢狀物件的修改能力。例如訂單明細應提供不可改動內部狀態的資料，移除明細則透過 `removeItem(itemId)` 檢查業務條件。函式內部獨自使用的暫存集合可就地修改。跨邊界交換的資料另遵循[邊界物件](../architecture/boundary-objects.md)。

## 註解與公開文件

優先以[名稱](naming.md)與程式結構表達行為。註解說明維護者從程式碼難以看出的理由、限制與依據。例如「供應商未提供冪等保證，請求送出後若結果未知，須先對帳」能解釋為何這個分支沒有重送。依據已在架構決策或外部契約中維護時，可簡述限制並連至來源。行為或依據變更時同步更新註解。

公開函式須提供呼叫者做決策所需的資訊。必要條件、業務效果、失敗與重試保證優先用型別與契約表達，其餘在公開介面旁說明或連至契約主要來源。例如保留多項庫存時，呼叫者須能查明任一品項不足會否全部回滾，以及以同一訂單重送的效果。簡單函式不必逐項重述參數；契約變更時同步維護文件。契約來源與相容性要求見[資料契約](../interfaces/data-contracts.md)。
