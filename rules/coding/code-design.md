# 程式碼設計與公開介面

<a id="function-responsibilities"></a>
## 函式責任與參數

依責任與變更原因決定是否拆分函式，保留清楚的流程入口。例如 `cancelOrder` 可協調取消與申請退款，但依付款方式計算退款金額的規則應由負責退款的元件維護。共通規範不訂固定行數上限。

參數必須讓讀者在呼叫處辨識操作意圖。多個布林值或相似參數容易混用時，可採具名參數、明確的選項型別，或拆成各自有意義的操作。有不合法的組合時，須以型別限制可表達的狀態。像 `setNotificationsEnabled(false)` 這類用途清楚的呼叫，可以保留布林參數。評估依據是意圖與組合是否合法，不訂固定參數數量上限。型別宣告遵循[型別安全](type-safety.md#嚴格檢查與明確宣告)。

<a id="visibility-and-state-ownership"></a>
## 可見性與狀態所有權

- 類別、函式與屬性依使用者採最小必要可見性。讀取與修改範圍分別決定，跨模組公開能力遵循[模組責任與公開入口](../architecture/module-boundaries.md#公開入口)。
- 無須改變的資料預設不可變。可變狀態須有明確擁有者，並以維護業務規則的操作修改。例如公開 `cancel()` 檢查取消條件，將直接寫入訂單狀態的能力留在內部。
- 讀取入口不可洩漏內部集合或巢狀物件的修改能力。例如訂單明細應提供不可改動內部狀態的資料，移除明細則透過 `removeItem(itemId)` 檢查業務條件。函式內部獨自使用的暫存集合可就地修改。跨邊界交換的資料另遵循[邊界物件](../architecture/boundary-objects.md#不可變性)。

<a id="comments-and-public-documentation"></a>
## 註解與公開文件

優先以[名稱](naming.md#領域詞彙與上下文)與程式結構表達行為。註解說明維護者從程式碼難以看出的理由、限制與依據。例如「供應商未提供冪等保證，請求送出後若結果未知，須先對帳」能解釋為何這個分支沒有重送。依據已在架構決策或外部契約中維護時，可簡述限制並連至來源。行為或依據變更時同步更新註解。

公開函式須提供呼叫者做決策所需的資訊。必要條件、業務效果、失敗與重試保證優先用型別與契約表達，其餘在公開介面旁說明或連至契約主要來源。例如保留多項庫存時，呼叫者須能查明任一品項不足會否全部回滾，以及以同一訂單重送的效果。簡單函式不必逐項重述參數；契約變更時同步維護文件。契約來源與相容性要求見[資料契約](../interfaces/data-contracts.md#主要定義來源)。

<a id="object-oriented-design-scope"></a>
## 物件導向設計的適用範圍

下列繼承、介面及建立方式的要求依實際採用的設計適用，不強制所有專案採用物件導向，也不要求增加介面、繼承或 Builder。語言特有的建構、可見性及覆寫限制由語言規範落實。

<a id="object-contracts"></a>
## 物件契約與維護責任

<a id="substitutability"></a>
<a id="cl-02"></a>

### 繼承的可替代性

繼承須具有明確的可替代關係，子型別不得破壞父型別承諾的輸入、結果與行為保證。僅為共用實作時，優先採用組合或委派，不以不成立的繼承關係換取程式碼重用；若子型別無法支援父型別承諾的操作，須重新檢視契約與能力劃分。

<a id="construction-entrypoints"></a>
<a id="cl-06"></a>

### 依需求選擇建立方式

建構子、具名工廠方法或 Builder 須依資料組合、建立語意與呼叫可讀性選擇，不強制每個類別使用工廠或 Builder。所有建立入口須一致保護必要條件，避免各自維護不一致的驗證。Builder 可暫存未完成的組裝資料，但不得產出無效的目標物件。

<a id="interface-capabilities"></a>
<a id="cl-08"></a>

### 介面的能力劃分

介面須依內聚的能力與使用端需求劃分，避免迫使使用端依賴無關操作，或迫使實作提供不支援的方法。不機械式拆成單一方法介面，共同服務同一責任的操作可保留於同一契約；不得以介面可見範圍取代執行期授權檢查。

<a id="acceptance"></a>
## 驗收

驗收案例的選擇與維護依[驗收共同原則](../quality/testing.md#acceptance-principles)。

<a id="supplementary-contract-acceptance"></a>
### 補充契約驗收

| 契約 | 驗收內容 |
| --- | --- |
| <a id="acceptance-substitutability"></a>[繼承的可替代性](#substitutability) | 以受影響的子型別或替代實作驗證父型別承諾的輸入、結果及必要檢查，確認替代後仍符合共同契約。 |
| <a id="acceptance-construction-entrypoints"></a>[依需求選擇建立方式](#construction-entrypoints) | 逐一驗證實際提供的建構子、工廠及 Builder 都執行一致的有效性檢查；組裝中資料不完整時不得產出無效目標物件。 |
| <a id="acceptance-interface-capabilities"></a>[介面的能力劃分](#interface-capabilities) | 核對實作能支援介面承諾的操作，沒有被迫提供不支援的方法；驗證介面劃分未取代操作所需的授權檢查。 |
| <a id="acceptance-document-contract"></a>[註解與公開文件](#註解與公開文件)、[實作註解與暫時處理](#implementation-notes) | 比對文件、註解與實際行為，確認使用端所需契約完整，理由與限制仍有效，暫時性處理有可追蹤事項。移除過時說明，避免僅重述名稱或複製多份契約。 |
