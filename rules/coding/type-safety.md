# 型別安全

<a id="strict-checks-and-explicit-types"></a>
## 嚴格檢查與明確宣告

- 支援靜態型別的語言必須啟用適用的嚴格型別與空值檢查；動態型別語言在可行範圍導入型別標註與靜態分析，具體要求由語言規範定義。
- 自行撰寫的程式碼必須明確宣告參數、回傳值、屬性、區域變數及集合元素的型別，不以自動推導取代標註。
- 匿名函式、解構、迴圈變數等語法的具體標註能力與做法，由語言規範確認。遇到能力限制時須個別決策，不自行豁免。
- 型別推導本身不等於弱型別；要求明確標註是本規範額外採用的可讀性與介面明確性要求。

<a id="no-type-check-bypasses"></a>
## 禁止主動繞過檢查

- 自行撰寫的程式碼，包括第三方整合元件，一律禁止主動繞過型別檢查。
- 不得透過不安全型別、未經檢查的強制轉型、無依據的斷言或忽略檢查指令消除型別錯誤。
- 未知資料必須使用安全的承接方式，經驗證與型別收窄後才使用；不得直接假定為預期型別。
- 工具或第三方套件限制須個別討論，依[例外核准流程](../workflow/rule-governance.md#exception-approval)處理，不預先開放整合處例外。

<a id="containers-and-generics"></a>
## 容器與泛型

- 固定結構資料必須使用明確資料型別，不得以任意鍵值容器代替。
- 真正動態的鍵值資料可以使用 Dictionary／Map，但鍵和值的型別都必須明確。
- 泛型必須表達真實型別關係，或搭配實際的解析與驗證機制。例如容器限制元素型別，或方法連結輸入與輸出的型別。
- 不得讓呼叫端只指定型別參數，就把未驗證資料當成該型別回傳；不得宣告實際無法保證的泛型結果。

<a id="type-conversions"></a>
## 型別轉換

- 可能改變語意、損失精度或掩蓋輸入錯誤的轉換，必須明確執行並驗證。
- 外部格式需要轉換時，由接收邊界依契約解析，檢查格式、範圍與精度。
- 轉換失敗必須回報錯誤，不得默默轉成 `0`、空值或其他預設值。
- 不得讓框架自動將不符合契約的輸入轉成可接受的值。
- 語言保證不損失資訊且不改變語意的安全轉換可以允許，具體範圍由語言規範定義。

專屬型別與狀態見[領域建模](domain-modeling.md#dedicated-types)，空值語意見[空值語意](nullability.md#null-state-semantics)。檢查與合併門檻見[規範驗證](../quality/rule-verification.md#verification-coverage)。

<a id="dynamic-type-contracts"></a>
## 動態能力的型別契約

<a id="dynamic-contract-validation"></a>
### 使用前驗證契約

動態元件須在適當的啟動、註冊或呼叫階段驗證能力、版本與型別契約。不符合時明確拒絕，不得僅憑名稱存在就執行，也不得靠未經驗證的轉型或任意替代掩蓋不相容。可提早確認的條件於啟動或註冊驗證，每次輸入才決定的條件則在執行前檢查。

<a id="acceptance"></a>
## 驗收

驗收案例的選擇與維護依[驗收共同原則](../quality/testing.md#acceptance-principles)。

- 自行撰寫的測試程式碼必須遵守相同型別安全規範，包括明確宣告、禁止型別逃逸與使用正確專屬型別。
- 測試不合法外部資料時，在接收邊界使用原始 JSON、字串或位元組等輸入。
- 測試專屬型別驗證時，傳入不合法原始值並確認建立失敗，不透過繞過型別檢查偽造有效的內部物件。
- 測試替身必須符合被替代介面的型別契約。
