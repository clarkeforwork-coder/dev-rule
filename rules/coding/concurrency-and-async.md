# 併發與非同步處理

適用於實際採用併發、平行或非同步的流程，包含程序內背景任務。不同語言可採不同執行模型；共享資料須維持同步與業務所需的原子性，不能以容器或單一欄位安全推定整段流程安全。

相關共同要求：[資源與元件生命週期](resource-lifecycle.md)、[錯誤處理](error-handling.md)、[效能與資源使用](../quality/performance.md)、[安全](../quality/security.md)、[日誌、稽核與可觀測性](../quality/observability.md)。必要例外依[規範治理](../workflow/rule-governance.md)處理。

## 契約要求

<a id="compound-atomicity"></a>
<a id="co-05"></a>

### 複合操作的原子性

共享集合上的複合操作須依業務條件明訂原子性範圍，使用適當的原子操作或同步機制維持保證。不得因集合本身具備執行緒安全性，就推定多步驟或跨資料結構的操作也安全；跨多個鍵、集合或物件的條件，由負責該條件的範圍協調。

<a id="task-ownership"></a>
<a id="ca-01"></a>

### 明確的工作擁有者

併發與非同步工作須有明確的生命週期擁有者，依[結果接收與故障處置](#async-result-reception)追蹤結果及處理失敗，並管理取消與資源。工作脫離原呼叫流程時，須明確移交責任，不得產生無人追蹤的背景工作，也不得將提交成功視為業務完成。不要求原請求等待所有工作完成，但獨立工作須由負責的背景元件接手。

<a id="async-result-reception"></a>

### 結果接收與故障處置

非同步結果依[錯誤處理](error-handling.md#失敗分類與表達)區分成功、業務失敗、技術故障及取消，明訂接收路徑，不得丟棄故障。

<a id="execution-resources"></a>
<a id="ca-02"></a>

### 統一管理執行資源

執行緒與任務執行資源須由明確元件統一配置及管理生命週期，不得在業務程式各處任意建立。透過明確提供的任務執行能力提交工作，依負載與隔離需求定義容量、排隊、拒絕及關閉策略。不強制全部共用同一執行資源；不論採用何種排程或執行緒機制，均須遵守資料庫連線及外部呼叫等下游限制。具體執行 API 由語言或框架規範落實。

<a id="deadline-budget"></a>
<a id="ca-04"></a>

### 等待期限與逾時處置

等待非同步結果須有明確期限，包含程序內背景任務的結果等待，並納入整體操作時間預算，不讓每一步重新取得完整期限。逾時後依契約取消、持續執行或移交結果追蹤責任，不得將等待結束視為工作已停止；未確認資源釋放前不得回收執行名額。長期背景服務可持續運作，但個別工作結果等待及服務關閉仍須定義期限與後續處置。

<a id="cancellation-and-termination"></a>
<a id="ca-05"></a>

### 取消傳遞與實際停止

取消須依契約傳遞至相關子工作，工作須配合停止與清理；不得將取消請求成功視為實際停止或副作用撤銷。無法停止或結果未確認的工作，仍須由明確擁有者追蹤至約定的完成條件，不得只取消最外層等待而遺留無人管理的工作。

<a id="task-completion-contract"></a>
<a id="ca-07"></a>

### 多工作組合的完成條件

多個非同步工作組合時，須明訂整體完成、成功與失敗條件，以及其他子工作的後續處置。部分成功或競速取結果須保留正確語意與對應關係，例如第一個成功不等於第一個完成。不得因整體流程已返回，就遺漏仍在執行工作的追蹤與清理。

<a id="execution-and-blocking"></a>
<a id="ca-08"></a>

### 執行位置與阻塞行為

非同步流程須確認各階段的執行資源與阻塞特性，避免占用受限資源等待同一資源上的工作完成。共用執行資源須評估競爭與隔離需求，不得因採用非同步 API 就推定不會阻塞或耗盡執行能力。不強制每個階段使用不同執行緒池，但執行安排、等待關係與容量須支撐流程完成。

<a id="context-propagation"></a>
<a id="ca-09"></a>

### 明確傳遞與清理脈絡

非同步工作所需的租戶、身分與追蹤脈絡須明確傳遞並限制範圍，不依賴未經保證的執行緒或任務區域狀態。可使用明確資料或已配置且驗證的框架機制，不假設脈絡自動沿用。設定的脈絡須在結束時正確清理或還原，避免共用執行資源洩漏資料；授權另依執行時契約確認，傳遞身分不代表權限持續有效。

<a id="lock-scope"></a>
<a id="ca-10"></a>

### 鎖定範圍與取得策略

鎖定範圍須完整保護必要條件，避免持鎖執行不受控的阻塞、等待或回呼。多鎖操作須明訂取得順序或避死鎖策略，所有退出路徑須正確釋放。不得為縮短持鎖時間將必要檢查移出保護範圍，破壞原子性。

## 驗收要求

依變更影響及實際採用能力驗證，測試層級與案例維護依[共通測試策略](../quality/testing.md)；不要求每個操作涵蓋全部情境，也不重測語言標準函式庫本身。

| 契約 | 驗收內容 |
| --- | --- |
| <a id="acceptance-compound-atomicity"></a>[複合操作的原子性](#compound-atomicity) | 對共享複合操作，以受控交錯或併發案例驗證約定的原子性及業務條件；跨鍵或跨集合的保證須驗證整個操作，不僅確認單一集合操作安全。 |
| <a id="acceptance-task-ownership"></a>[明確的工作擁有者](#task-ownership) | 核對每項工作及脫離原呼叫流程後的擁有者，確認責任移交明確，結果、失敗、取消與資源均有負責元件追蹤，不留下無人接手的工作。結果的分類與接收路徑另見[結果接收與故障處置驗收](#acceptance-result-reception)。 |
| <a id="acceptance-result-reception"></a>[結果接收與故障處置](#async-result-reception) | 核對成功、業務失敗、技術故障及取消的接收路徑，確認結果分類保留且故障未被丟棄。工作擁有者與責任移交另見[明確的工作擁有者驗收](#acceptance-task-ownership)。 |
| <a id="acceptance-execution-resources"></a>[統一管理執行資源](#execution-resources)、[執行位置與阻塞行為](#execution-and-blocking) | 核對實際執行配置、各階段執行位置及阻塞關係。依風險模擬容量耗盡、排隊與拒絕，確認不超出下游限制，也不因同一受限資源上的相互等待而無法前進。 |
| <a id="acceptance-deadline-cancellation"></a>[等待期限與逾時處置](#deadline-budget)、[取消傳遞與實際停止](#cancellation-and-termination) | 驗證期限承接整體預算，逾時與取消後工作依契約停止或受控繼續。確認相關子工作收到所需訊號，未確認停止的工作仍有擁有者，執行名額依實際資源釋放回收。 |
| <a id="acceptance-task-composition"></a>[多工作組合的完成條件](#task-completion-contract) | 以不同完成順序及子工作失敗驗證全部成功、部分成功或競速等適用契約。核對每項結果與來源對應，剩餘工作持續受到管理，未將最快失敗當成第一個成功。 |
| <a id="acceptance-context-isolation"></a>[明確傳遞與清理脈絡](#context-propagation) | 在共用執行資源上交錯執行不同租戶或身分的工作，驗證脈絡正確傳遞，成功、失敗與取消後均清理或還原，沒有跨工作污染。核對延後執行的授權仍依契約確認。 |
| <a id="acceptance-lock-scope"></a>[鎖定範圍與取得策略](#lock-scope) | 以受控交錯核對鎖定範圍完整保護必要條件；檢查多鎖取得策略、所有退出路徑的釋放及持鎖期間的阻塞或外部回呼，不以偶然成功代替鎖定設計依據。 |

## 共同生命週期

元件就緒、依賴生命週期及受控關閉由[資源生命週期](resource-lifecycle.md)維護；結果接收及完成責任依[結果接收與故障處置](#async-result-reception)及[明確的工作擁有者](#task-ownership)。
