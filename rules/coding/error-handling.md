# 錯誤處理

本文件定義跨語言的失敗分類、傳遞與處置原則。重試與冪等遵循[外部整合可靠性](../interfaces/external-services.md)，事件恢復遵循[事件可靠性](../interfaces/events.md)。具體結果型別、例外與取消機制由語言規範定義；專案的補償與恢復實作另行指定。

## 失敗分類與表達

- 依失敗原因與業務語意分類，不只看底層是否拋出例外。
- 預期的業務失敗必須使用明確結果型別，提供可辨識的原因，例如庫存不足或訂單狀態不允許取消。呼叫端必須處理結果，不解析錯誤文字，也不得以空值或單純 `false` 隱藏原因。
- 非預期的技術故障透過例外機制傳遞，不得偽裝成一般業務失敗。
- 框架或第三方以例外表達已知業務失敗時，由銜接元件辨識並轉換；不得將所有例外一律轉成業務失敗。例如只有明確辨識為帳號重複的唯一性限制衝突，才能轉成「帳號已存在」。
- 取消是獨立的控制結果，不一律視為系統故障，也不得回報成功。

結果型別須遵循[型別安全](type-safety.md)與[狀態建模](domain-modeling.md)，對外呈現須符合[資料契約](../interfaces/data-contracts.md)。

## 捕捉與處置責任

- 只有能採取明確處置的地方才捕捉例外，不要求每層捕捉。
- 明確處置包括執行已定義的恢復或補償、在邊界轉換已知錯誤，以及由 API、背景工作或訊息處理的最外層入口結束失敗操作。
- 不得捕捉後忽略錯誤、假裝成功，或無依據地回傳空值與預設值。
- 不為逐層記錄日誌而反覆捕捉並重新拋出。
- 資源釋放優先使用語言或框架的資源管理機制，不得因此吞掉例外。

## 原因保留與錯誤轉換

- 包裝或轉換例外時，必須保留原始原因、例外鏈與堆疊，不只複製錯誤文字。
- 補充必要的操作脈絡，例如失敗操作、外部服務名稱或追蹤識別碼。
- 不得將密碼、Token、完整付款資料或其他敏感內容加入例外訊息。
- 只有需要轉換抽象層次或補充有效脈絡時才包裝，不逐層無意義地更換例外。
- 不得改變錯誤語意。例如付款呼叫逾時不能轉成「付款遭拒」。
- 診斷資訊供內部處理，對外回應仍遵守既有資訊揭露限制，不直接輸出內部例外。

## 故障日誌責任

- 由對該次處理結果負責的元件統一記錄故障，避免每層重複記錄相同堆疊。
- 例外繼續向上傳遞時，下層補充必要脈絡，不重複記錄相同故障；入口在判定操作失敗時記錄。
- 中途已完成恢復時，由恢復元件依需要記錄恢復結果，不再當成未處理故障上報。
- 預期業務失敗不一律記為系統錯誤，依監控、稽核或安全需求決定記錄方式。
- 跨服務各自記錄自己的處理結果，以共同追蹤識別碼串連，不要求分散式流程只能有一筆日誌。

日誌層級、追蹤欄位與故障告警依[日誌、稽核與可觀測性](../quality/observability.md)制定。

## 降級與替代結果

- 只有事先定義且符合業務語意的情境才允許降級，必須定義替代來源、有效期限與使用限制。
- 替代結果若會影響使用端判斷，契約必須表達資料過期、結果不完整或功能降級。
- 涉及授權、扣款或庫存承諾等操作，不得以預設成功繞過必要確認。
- 降級不可用或不符合條件時，必須明確回報失敗，不得用替代值掩蓋故障。
- 降級成功仍須保留適當監控資訊，避免長期故障被隱藏。

## 結果未知

- 逾時或連線中斷只表示未取得結果，不代表對方未執行；必須區分確定失敗與結果未知，不得直接當作成功或業務失敗。
- 對可能產生副作用的操作，不得未經確認就重複執行。
- 必須事先定義後續確認方式，例如依操作識別碼查詢、等待結果事件或對帳。
- 對外契約依實際語意表達「處理中」或「結果待確認」；沒有仍在處理的依據時，不得僅因結果未知就宣稱處理中。
- 自動重試必須符合[安全重試與冪等要求](../interfaces/external-services.md)，不得只因逾時而重送；確認契約保證相同操作識別碼可安全重送後，才可依該機制處理。

## 多步驟與部分成功

- 操作契約必須事先定義「全部成功才成立」或「允許部分成功」，不得失敗後才臨時改變語意。
- 全部成功才成立的操作，失敗時依[交易邊界](../data/transactions.md)及[跨步驟失敗與業務補償](../workflow/compensation.md)處理；回復尚未完成，不得宣稱已全部撤銷。
- 允許部分成功時，明確回報各項目的成功、失敗或結果未知狀態，以及對應識別資訊。
- 不得只回傳整體成功而隱藏項目失敗。
- 後續重試只針對可安全重試的項目，不直接重跑已成功的操作。

## 失敗後狀態

批次修改須明訂失敗後狀態，不得假設拋例外即未修改；不要求所有集合操作具備交易能力。全部成功或部分成功及各筆對應依[多步驟與部分成功](#多步驟與部分成功)。

## 取消

- 取消訊號應傳遞給支援取消的下游操作，停止不必要工作並釋放資源。
- 不得捕捉取消訊號後繼續執行被取消的操作，或自動重試；必要的清理、結果確認與既定補償仍須處理。
- 取消不代表既有副作用自動撤銷。已送出付款或提交資料時，仍須確認結果，必要時執行既定補償。
- 業務要求啟動後持續完成的流程，必須明確設計為獨立背景流程並提供結果查詢，不得暗中忽略取消。

## 清理與補償失敗

- 清理或補償失敗不得覆蓋原始錯誤，必須保留兩者關係與必要操作識別資訊。
- 仍可安全釋放的其他資源應繼續嘗試釋放，不能因一項清理失敗就略過全部。
- 補償失敗時明確標示尚未恢復一致性，不得回報已全部撤銷。
- 必須指定後續恢復或人工處理責任，不能只留下日誌就視為完成。
- 對外依契約提供安全狀態，內部保留完整失敗關係供診斷。

## 程式缺陷與不變條件

- 發現程式缺陷或內部不變條件遭破壞時，必須停止受影響操作，不得以預設值修補後繼續。
- 不得將程式缺陷轉成一般業務失敗，例如將內部空值錯誤回報為使用者不存在。
- 不自動重試明顯的邏輯錯誤，避免反覆執行相同缺陷。
- 保留診斷資訊，交由既定故障記錄與監控機制處理。
- 停止或隔離範圍依影響決定：單一請求故障通常結束該請求；共用狀態不可信時停止相關處理或由框架隔離，不一律要求整個程序退出。

驗證與驗收要求見[本文件驗收](#acceptance)。偏離本規範須依[規範治理](../workflow/rule-governance.md)核准，不得自行放寬。

## 動態呼叫的故障分類

<a id="dynamic-failure-classification"></a>
<a id="rf-05"></a>

### 區分故障與執行結果

動態載入與呼叫須區分目標解析、存取或契約檢查失敗，以及目標執行期間的故障，保留原始原因與執行脈絡。不得將所有失敗統一視為目標不存在，也不得未確認執行結果與重試安全性就改用其他目標或重新執行；外層收到例外不代表目標未執行或未產生副作用。

<a id="acceptance"></a>
## 驗收

<a id="錯誤處理驗證與驗收"></a>

依操作風險、實際邊界、副作用與重要業務流程，驗證[錯誤處理](../coding/error-handling.md)的適用失敗路徑，不只測試成功流程，也不要求每個函式套用所有故障情境。

- 預期業務失敗回傳正確結果，技術故障與程式缺陷不被誤分類或吞掉。
- 逾時、結果未知與取消不被誤報為成功或確定失敗。
- 部分成功、降級與補償失敗符合契約，不隱藏未完成事項。
- 必要資源確實釋放，原始錯誤未被清理錯誤覆蓋。
- 對外回應不洩漏敏感資訊，內部保留必要診斷資訊。

測試程式碼同樣遵守[型別安全](../coding/type-safety.md)，具體要求見[測試程式碼](type-safety.md#acceptance)。

### 補充契約驗收

依變更影響及實際採用能力驗證，測試層級與案例維護依[共通測試策略](../quality/testing.md)；不要求每個操作涵蓋全部情境，也不重測語言標準函式庫本身。

| 契約 | 驗收內容 |
| --- | --- |
| <a id="acceptance-dynamic-failure"></a>[區分故障與執行結果](#dynamic-failure-classification) | 分別觸發適用的解析、存取、契約及目標執行故障，確認原因與分類保留，未將已執行的故障誤當未找到目標，且未進行無安全依據的替換或重跑。 |
| <a id="acceptance-failure-state"></a>[失敗後狀態](#failure-state-guarantee) | 觸發批次修改的適用失敗路徑，核對例外後實際狀態符合約定，不以拋例外推定未修改，也不要求所有集合操作具備交易能力。全部或部分成功及項目對應另見[多步驟與部分成功驗收](#acceptance-partial-operation)。 |
| <a id="acceptance-partial-operation"></a>[多步驟與部分成功](#多步驟與部分成功) | 在處理中途製造適用的失敗，核對實際狀態是否符合全部成功或部分成功保證；允許部分成功時，結果須能對應已完成、未完成或結果未知的項目，不隱藏項目失敗或未完成事項。集合批次修改適用同一驗收。批次修改拋出例外後的狀態另見[失敗後狀態驗收](#acceptance-failure-state)。 |
