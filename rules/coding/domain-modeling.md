# 領域建模

## 專屬型別

- 容易混用或具有業務約束的值必須使用專屬型別，例如不同用途的 ID、包含幣別的金額、帶單位數值與受限制的日期區間。
- 專屬型別必須實際阻止誤用；僅為原始型別取別名、卻仍可任意互換，不符合要求。
- 建立時必須驗證該值的格式與適用限制，建立後不得透過任意修改破壞有效性。
- 相關參數、屬性與回傳值必須使用專屬型別，不得建立後又在內部介面退回一般字串或數字，失去隔離效果。
- 在資料庫、API 等邊界依契約轉換成外部格式。
- 一般描述性資料，例如備註，可使用明確的原始型別，不要求全部包裝。

型別有效不等於業務操作有效。例如使用者 ID 格式正確，不表示使用者存在或操作者有權存取，這些條件仍須另行驗證。

## 狀態建模

- 互斥狀態必須使用明確的狀態型別，不得以多個獨立布林值表達可互相矛盾的狀態。
- 不同狀態需要不同資料時，分別以型別表達必要資料。例如付款成功需要交易編號，失敗需要失敗原因。
- 狀態轉換必須透過明確業務操作，執行必要檢查，不得任意修改狀態欄位繞過規則。
- 單純二元屬性，例如是否訂閱電子報，仍可使用布林值。

驗證應確認錯誤型別不能誤用、無效值建立失敗，以及狀態轉換維持業務條件。語言實作方式另訂，例外依[規範治理](../workflow/rule-governance.md)處理。

## 值語意、狀態與操作結果

<a id="vo-03"></a>

### 不可變性

專屬值型別與領域值物件建立後須維持不可變，值的變更以產生符合驗證及正規化規則的新物件表達。不得透過可變欄位或外洩參考間接修改內容；必要時使用不可變資料、封裝或防禦性複製，涵蓋傳入及取出路徑，不強制全面深層複製。只有外層唯讀不代表內含資料不可變。本要求不強制 Entity 不可變；具有身分及生命週期的實體仍可透過受控業務操作修改狀態。

<a id="vo-05"></a>

### 正規化規則

需要正規化時，須明訂轉換規則及其與驗證、相等性的關係，並由所有建立入口一致執行。不得進行未經契約允許的修剪、大小寫轉換、精度調整或範圍修正來掩蓋不合法輸入。

<a id="vo-06"></a>

### 運算責任

涉及值本身語意的運算，須集中於值物件或責任明確的領域元件，保留必要的型別、單位與有效性約束。結果須符合值型別的建立規則，不得由使用端拆出底層值後各自繞過或重複實作。邊界映射、呈現等必要用途仍可讀取底層值；跨幣別換算等依賴外部資料或政策的操作，由負責元件協調，不要求值物件自行查詢外部資料。

<a id="vo-07"></a>

### 資料還原

反序列化、持久化還原與框架映射須維持值物件的不變條件，不得繞過必要驗證與正規化。歷史資料不符合目前規則時，須透過明確的版本、遷移或相容處理，不得直接建立違反現行契約的物件，也不得默默以目前預設值推測歷史資料。具體框架配置由 Framework 規範與專案落實。

<a id="st-04"></a>

### 結果與目前狀態分開表達

操作結果須表達本次操作的處理結果，不得僅以物件狀態代替。契約需要區分成功、重複操作、拒絕或尚未完成時，須明確建模，不得將已受理視為業務完成。結果型別只包含使用端所需的區別與資料，不要求每次操作都建立複雜結果物件。

<a id="st-06"></a>

### 處理完整性

狀態與結果的使用端須明確處理契約要求的情況，不得以預設分支將新增、未知或未處理的情況當成成功或默默忽略。多種情況可共用處理方式，但須有明確語意依據。優先利用適用版本的編譯檢查，並由測試與審查補足工具無法涵蓋的部分。

<a id="st-08"></a>

### 封閉或允許擴充

狀態與結果模型須明訂是封閉集合或允許擴充。封閉集合須以語言提供的型別機制，或可見性、建立入口與檢查控制實作及建立範圍。允許擴充時，須定義擴充契約及未知實作的處理方式，不得同時假設所有結果已完整列舉。不強制所有語言或版本採用相同語法，具體落實由語言規範定義。

<a id="st-09"></a>

### 結果保留當時事實

操作結果須穩定表達產生當時可確認的事實，必要資料不得因外部可變參考而改變。只保留契約所需資訊，不要求複製完整物件；最新狀態另行查詢，不以持有可變業務物件代替結果資料。

<a id="st-10"></a>

### 模型驗收

狀態與結果模型新增或變更時，須驗證受影響的合法轉換、拒絕、重複操作、必要資料與使用端分支，以及適用的外部代碼映射。同時確認結果與實際狀態、副作用一致，不僅測試型別建立成功，也不要求涵蓋所有無業務意義的排列組合。

<a id="eq-01"></a>

### 明訂比較語意

相等判斷須先明訂比較的是物件身分、業務實體身分或值內容。相等操作的語意須與型別契約一致；內容比對或版本一致性若是不同需求，應另提供明確操作，不混入同一套相等性。同一筆業務實體不代表不同時間載入的內容完全一致，Entity 也不得未經判斷就將所有欄位納入相等性。

<a id="eq-04"></a>

### Entity 識別碼的生命週期

Entity 若以識別碼定義相等性，須明訂識別碼產生前後的比較規則，不得因兩者識別碼皆缺值就判定相等。建立時即具備穩定識別碼，或持久化後才取得識別碼，須各自明訂適用規則與使用限制；識別碼變化不得破壞集合契約。沒有跨實例相等需求時，不強制自訂相等操作。

## 補充契約驗收

依變更影響及實際採用能力驗證，測試層級與案例維護依[共通測試策略](../quality/testing.md)；不要求每個操作涵蓋全部情境，也不重測語言標準函式庫本身。

| 契約 | 驗收內容 |
| --- | --- |
| <a id="acceptance-value-3"></a>[不可變性](#vo-03) | 對含可變資料的型別，修改傳入或取出的資料，確認原值物件未受影響。檢查封裝與必要的複製，不能只檢查外層欄位是否為唯讀。 |
| <a id="acceptance-value-5"></a>[正規化規則](#vo-05) | 以不同合法表示及不合法輸入驗證正規化、驗證順序與相等性符合契約，所有建立入口結果一致，沒有未授權的修剪或數值修正。 |
| <a id="acceptance-value-6"></a>[運算責任](#vo-06) | 驗證適用運算的結果、單位與有效性限制，原物件維持不變。確認不相容的值依契約拒絕或處理，使用端未各自拆值繞過規則。 |
| <a id="acceptance-value-7"></a>[資料還原](#vo-07) | 經實際採用的反序列化、持久化或框架映射路徑驗證合法與不合法資料。涉及歷史資料時，確認按明訂版本或遷移規則還原，不產出違反契約的物件。 |
| <a id="acceptance-state-4-5"></a>[結果與目前狀態分開表達](#st-04)、[失敗分類](error-handling.md#失敗分類與表達) | 驗證成功、重複操作、拒絕及未完成等適用結果。核對必要原因與資料可由型別判斷，業務完成與已受理有所區別，技術故障未被轉成一般拒絕。 |
| <a id="acceptance-state-6-8"></a>[處理完整性](#st-06)、[封閉或允許擴充](#st-08) | 核對模型的封閉或擴充契約與實作限制，審查受影響的使用端分支。模型新增情況時確認適用檢查能發現未處理處，工具未涵蓋者由測試與審查補足；未知或擴充結果不得落入假成功。 |
| <a id="acceptance-state-9"></a>[結果保留當時事實](#st-09) | 在結果產生後改變來源業務物件或其他可變資料，確認結果仍保留當時事實；核對結果只含必要資訊，最新狀態透過獨立查詢取得。 |
| <a id="acceptance-state-10"></a>[模型驗收](#st-10) | 核對測試涵蓋變更影響的轉換、拒絕、重複操作、資料及分支；以實際狀態與必要副作用驗證結果，而不只檢查回傳型別或成功標記。 |
| <a id="acceptance-identity-semantics"></a>[明訂比較語意](#eq-01) | 核對比較用途是否為物件身分、實體身分或值內容，確認內容比對與版本一致性沒有誤用實體識別。 |
| <a id="acceptance-identity-lifecycle"></a>[Entity 識別碼的生命週期](#eq-04) | 對適用的 Entity 驗證識別碼尚未產生、產生後及變更時的相等與集合行為；缺值識別碼不得使不同實體被誤判為相等。 |
| <a id="acceptance-value-validity"></a>[專屬型別](#專屬型別) | 審查專屬型別能否阻止業務概念混用，相關介面有無退回一般字串或數字。驗證合法值、邊界值及不合法值，確認建立成功後符合自身規則，且未將格式有效誤當成存在性或授權成立。 |
| <a id="acceptance-state-data"></a>[狀態建模](#狀態建模) | 核對互斥狀態由明確型別表達，必要資料由對應型別保護。確認不能建立契約禁止的狀態與資料組合，不以僅存在狀態碼作為符合依據。 |
| <a id="acceptance-state-transition"></a>[狀態建模](#狀態建模) | 驗證允許與不允許的來源狀態、前置條件及轉換後資料。確認公開介面沒有可繞過規則的任意設定路徑，拒絕時未產生不應發生的副作用。 |
| <a id="acceptance-value-coverage"></a>[模型驗證與還原](#模型驗證與還原) | 核對測試涵蓋受影響值型別的建立、邊界值、相等性、不可變性及適用的運算與還原，不以只有建立成功的案例代替驗收。 |

## 模型驗證與還原

專屬型別須驗證建立、邊界值、相等性、不可變性及適用的運算與還原行為，不能只測建立成功。不同業務面向應分別建模再明訂相互限制，例如付款與配送不強行合併為單一狀態；狀態轉換須核對來源狀態、必要條件及轉換後資料。外部存在性與授權仍由負責業務元件驗證。數值、時間及文字處理細節依[共同資料語意](numbers-dates-text.md)。
