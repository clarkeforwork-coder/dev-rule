# 領域建模

## 專屬型別

- 容易混用或具有業務約束的值必須使用專屬型別，例如不同用途的 ID、包含幣別的金額、帶單位數值與受限制的日期區間。
- 專屬型別必須實際阻止誤用；僅為原始型別取別名、卻仍可任意互換，不符合要求。
- 建立時必須驗證該值的格式與適用限制，建立後不得透過任意修改破壞有效性。
- 相關參數、屬性與回傳值必須使用專屬型別，不得建立後又在內部介面退回一般字串或數字，失去隔離效果。
- 在資料庫、API 等邊界依契約轉換成外部格式。
- 一般描述性資料，例如備註，可使用明確的原始型別，不要求全部包裝。

型別有效不等於業務操作有效。例如使用者 ID 格式正確，不表示使用者存在或操作者有權存取，這些條件仍須另行驗證。

## 狀態建模

- 互斥狀態必須使用明確的狀態型別，不得以多個獨立布林值表達可互相矛盾的狀態。
- 不同狀態需要不同資料時，分別以型別表達必要資料。例如付款成功需要交易編號，失敗需要失敗原因。
- 狀態轉換必須透過明確業務操作，執行必要檢查，不得任意修改狀態欄位繞過規則。
- 單純二元屬性，例如是否訂閱電子報，仍可使用布林值。

驗證應確認錯誤型別不能誤用、無效值建立失敗，以及狀態轉換維持業務條件。語言實作方式另訂，例外依[規範治理](../workflow/rule-governance.md)處理。
