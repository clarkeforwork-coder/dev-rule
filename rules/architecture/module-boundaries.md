# 模組責任與公開入口

<a id="business-responsibilities"></a>
## 業務責任劃分

- 優先依業務能力與責任劃分模組，例如訂單、付款與庫存，而非只依技術種類分類。
- 同一業務目的且經常一起變動的邏輯優先集中；不同業務責任、可各自演進的部分保持明確邊界。
- 模組不等於獨立服務或部署單位，不強制特定目錄排列或多套件結構。
- 每項業務規則與核心資料的變更必須有明確的管理模組。其他模組不得複製其決策邏輯、繞過公開能力或直接修改其資料。
- 唯一管理歸屬指業務決策不能散落並各自演進，不表示所有輸入檢查只能出現一次。

<a id="public-entry-points"></a>
## 公開入口

- 必須區分公開能力與內部實作；其他模組只能使用公開入口，不得直接引用內部 Repository、輔助類別或流程實作。
- 每個專案必須統一定義公開入口的形式、位置、命名與允許公開的內容。同類型模組遵循同一慣例，偏離須經核准，不由各開發者自行選擇。
- 公開能力維持最小必要範圍，不為方便呼叫而全面公開。
- 入口可以是介面、應用服務或模組匯出項目。是否增加包裝層由專案架構統一決定，不強制增加只有轉呼叫用途的元件。
- 語言上的公開可見性不必然代表模組公開 API；因框架需要而公開的內部類別仍不得被其他模組任意引用。
- 優先以語言、模組或建置工具限制存取；工具不足時以架構檢查與審查補足。
- 資料交換遵循[邊界物件](boundary-objects.md#separation)，契約所有權遵循[共用型別管理](shared-types.md#type-ownership)。

<a id="cross-module-workflows"></a>
## 跨模組流程

- 由明確指定的流程負責元件協調執行順序與失敗處理，各模組執行自己擁有的業務能力。
- 協調元件不得複製各模組的業務規則。例如庫存是否足夠由庫存模組判斷，協調元件負責呼叫與處理結果。
- 不強制建立獨立協調服務，可依架構放在應用服務、使用案例或工作流程元件。
- 採事件協作時，即使沒有中央協調者，也必須記錄整體流程、各步驟責任、終止條件與失敗處理，不能失去管理歸屬。

跨模組查詢見[資料存取邊界](../data/persistence.md#module-boundaries)，一致性責任見[交易邊界](../data/transactions.md#transaction-ownership)。
