# 邊界物件

<a id="scope"></a>
## 適用範圍

資料邊界涵蓋外部輸入與輸出、業務模組之間、架構層之間、第三方整合，以及事件與訊息。模組指具有獨立業務責任的單位，不是每個資料夾。

專案必須依所選架構定義實際邊界與責任，不預設必須具有特定名稱的應用層、領域層或持久化層。

<a id="separation"></a>
## 隔離與拆分

- 依資料的責任、語意、欄位、驗證要求與變更原因判斷隔離需求，不強制每跨一層都建立新的 DTO。
- 對外 API 的 Request 與 Response 必須分開定義，即使目前欄位相同；語意一致的值型別可以共用。
- 禁止直接將資料庫 Entity 或 ORM Model 作為對外 API Response，必須轉成明確的輸出模型。
- 跨業務模組必須透過公開資料契約交換資料，不得直接暴露內部領域物件。共用值型別須符合[共用型別管理](shared-types.md#type-ownership)。
- 第三方服務契約型別必須限制在整合元件內，經驗證與轉換後，才交給內部業務邏輯使用。日期或數學等通用函式庫型別不因此一律禁止，另依套件政策判斷。

模組內部依專案架構決議決定物件傳遞範圍，不強制每次方法呼叫都轉 DTO。ORM Model 的內部使用仍須符合技術隔離與依賴方向；此內部彈性不豁免對外 API 及跨模組使用公開資料契約的要求。

<a id="immutability"></a>
## 不可變性

邊界物件預設不可變，包含內含集合與巢狀資料。接收端需要調整資料時，建立新物件，不修改其他使用端可能持有的資料。僅將外層宣告為唯讀，卻允許修改內層資料，不符合本要求。

本要求針對交換資料的物件；領域實體透過業務操作改變狀態，依[領域建模](../coding/domain-modeling.md#state-modeling)處理。

<a id="minimal-fields"></a>
## 明確列出、最小必要

- Request 只接受該操作允許設定的欄位，不能藉由一般資料更新操作修改角色或權限等未授權欄位。
- Response 只提供用途需要且使用端有權取得的欄位，不因內部已有資料就全部輸出。
- 不以大量選填欄位的通用 DTO 同時承擔不同用途，應依契約責任拆分。
- 來源新增欄位不得自動擴大跨邊界傳遞範圍，映射要求見[資料映射](data-mapping.md#conversion-requirements)。

<a id="acceptance"></a>
## 驗收

驗收案例的選擇與維護依[驗收共同原則](../quality/testing.md#acceptance-principles)。

審查時應確認拆分理由、敏感欄位與可修改欄位範圍，以及集合與巢狀資料是否仍可被外部修改。偏離要求須依[例外核准流程](../workflow/rule-governance.md#exception-approval)處理。

<a id="supplementary-contract-acceptance"></a>
### 補充契約驗收

| 契約 | 驗收內容 |
| --- | --- |
| <a id="acceptance-boundary-separation"></a>[隔離與拆分](#separation) | 審查邊界物件的契約責任與隔離依據，確認未因欄位相同而不當共用，也未僅因分層而重複建立 DTO。確認公開資料未直接暴露持久化或模組內部模型。 |
| <a id="acceptance-boundary-isolation"></a>[不可變性](#immutability) | 修改來源或目標的可變集合及適用的可變元素，確認另一方保持所需隔離；共用不可變值時核對其不可變性與共用契約，不以全面複製作為唯一合格方式。 |
