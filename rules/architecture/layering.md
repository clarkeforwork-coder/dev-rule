# 架構分層與依賴方向

<a id="architecture-decisions"></a>
## 專案架構決策

每個專案必須記錄採用的架構、選擇理由、各層與模組的責任邊界，以及允許的依賴方向。選擇應考量業務複雜度、變更需求、團隊與維護成本，不只依專案大小判斷。

文件深度依專案複雜度調整，小專案可以用簡短文件說明，不要求為符合規範增加分層。通用規範不預設特定分層名稱或固定目錄。

<a id="layer-calls"></a>
## 分層與跨層呼叫

- 跨層呼叫必須符合專案明確宣告的依賴規則，不一律要求逐層轉呼叫。
- 不得繞過必要業務責任。例如修改訂單不能直接從 API 入口更新資料庫而略過業務檢查。
- 單純查詢在架構允許時可透過專用查詢元件取得資料，仍須執行必要授權與資料範圍限制。
- 不為形式建立沒有實際責任、只原樣轉呼叫的中間層。允許路徑必須記錄於架構文件，不由個別開發者臨時決定。

<a id="business-technical-responsibilities"></a>
## 業務與技術責任

核心業務規則不得直接承擔 HTTP 解析、SQL／ORM 操作、訊息傳輸或第三方 SDK 呼叫等技術責任，應由職責明確的元件提供所需能力。

- 三層式架構可由業務層使用資料存取元件，將持久化操作留在資料存取層。
- 整潔架構可由核心定義所需抽象，再由外層提供實作，使原始碼依賴符合架構方向。
- 不強制所有專案都建立介面、採用依賴反轉或禁止一切框架標註；具體依賴限制由專案架構決定。
- 框架使用與組裝方式遵循[框架與依賴組裝](dependency-composition.md#framework-first)。

<a id="cycle-restrictions"></a>
## 循環限制

- 禁止業務模組的程式碼依賴形成直接或間接循環。
- 禁止同一條同步處理鏈繞回已參與服務的同步呼叫循環。
- 微服務不得引用其他服務的內部實作，應透過公開 API 或訊息契約互動。
- 允許具有明確終點與失敗處理的非同步業務往返，必須處理重複訊息並避免無限事件回圈。雙向訊息交換不直接等同程式碼循環依賴。
- 發現循環時，依原因調整責任歸屬、引入流程協調或適當抽象與事件；不得僅替換呼叫形式而保留責任糾纏。

例如訂單提出付款請求、付款發布結果、訂單更新狀態並結束流程，可以是允許的非同步往返。流程責任見[模組責任與公開入口](module-boundaries.md#cross-module-workflows)。

依賴驗證見[本文件驗收](#acceptance)，架構變更與例外見[規範治理](../workflow/rule-governance.md#exception-approval)。

<a id="acceptance"></a>
## 驗收

驗收案例的選擇與維護依[驗收共同原則](../quality/testing.md#acceptance-principles)。

<a id="架構檢查與可測試性"></a>

- 可自動判斷的架構依賴限制必須納入 CI，包括引用其他模組內部元件、禁止的跨層依賴、循環依賴、核心引用架構禁止的技術實作，以及共用元件反向依賴業務模組。
- 業務責任是否合理、模組是否應拆分等語意問題由人工審查，不只依靠工具。
- 微服務實際呼叫鏈須搭配整合驗證與執行期追蹤，不能只靠程式碼依賴分析判斷同步呼叫循環。
- 工具依專案選擇，既有違規沿用漸進導入機制。
