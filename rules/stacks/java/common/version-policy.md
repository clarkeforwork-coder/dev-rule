# Java 適用範圍與版本判定

本文件只維護 Java 的具體要求；引用的共通規範同樣具有約束力。

適用於 Java 應用程式、共用函式庫及多模組專案。以下要求由各專案依實際建置、交付及執行方式落實，並承接[開發共通規範](../../../README.md)。

## 版本宣告與相容性

1. **分別記錄版本資訊**。專案須記錄建置 JDK、編譯目標與標準函式庫 API 相容範圍，以及實際部署或承諾支援的 Java 執行版本。共用函式庫須明列使用端可依賴的支援範圍。
2. **建置設定落實限制**。版本與相容性要求須寫入受版本控制的建置設定，本機與 CI 遵循一致規則。編譯時須限制允許的語言功能、標準 API 及產物位元碼格式。具體設定方式依適用 Java 版本及建置工具制定。
3. **執行版本驗證**。每個承諾支援的執行版本須有實際驗證依據，涵蓋適用的產物啟動、關鍵行為與依賴載入。函式庫須在使用端執行環境驗證載入與關鍵功能。驗證深度依風險決定，結果記錄於 CI 或發布流程。
4. **多模組版本要求**。各模組可依部署與使用需求採不同版本要求，但須逐模組明訂編譯目標、支援範圍及依賴關係。共用模組須符合使用端承諾的相容範圍，並完成對應驗證。

例如，建置 JDK 與部署環境使用 Java 21，而產物承諾相容 Java 17 時，編譯須維持 Java 17 的語言、API 及位元碼限制，並有 Java 17 與實際部署環境的驗證依據。

## 依賴、升級與特殊功能

5. **依賴版本要求**。新增或升級依賴時，須核對直接與間接依賴的 Java 版本要求。若超出專案承諾的執行範圍，須先決定保留相容版本、替換依賴或安排專案升級，完成相容性處置後才能採用。[第三方套件與依賴管理](../../../workflow/dependencies.md)
6. **建置升級與支援範圍變更**。升級建置 JDK 須維持既有相容承諾。提高最低執行版本須獨立評估部署環境、函式庫使用端與回退需求，明訂遷移順序並完成驗證。對外提供的函式庫須明確告知新的最低版本。
7. **Preview 功能**。專案預設使用正式發布的語言功能與 API。採用 Preview 功能須由專案負責人核准，記錄用途、理由與影響範圍，明訂建置、測試、部署配套及後續升級的維護責任。環境配套無法滿足時，先採正式功能完成需求。
8. **JDK 內部實作與存取限制**。專案預設依賴公開且受支援的 JDK API。需要存取內部實作或放寬存取限制時，須依例外流程個別核准，記錄原因、範圍、相關依賴與替代方案，明訂後續處置，並於 JDK 升級時重新驗證。
9. **棄用 API**。新增或修改程式須優先採用符合專案版本範圍的替代 API。既有棄用 API 依移除風險與影響安排遷移，特別檢視已標示預定移除的項目。必要的持續使用須經例外核准，記錄原因、適用範圍與重新評估條件。

Preview 的採用紀錄及其他例外均依[規範治理](../../../workflow/rule-governance.md#例外核准)管理。既有程式碼依相同文件的漸進導入要求處理。

## 工具、環境與發布追溯

10. **建置與驗證工具相容性**。Java 版本變更須評估參與編譯、測試、分析及產物處理的工具，包含適用的建置工具、編譯外掛、註解處理器、測試執行器與覆蓋率工具。須確認必要檢查實際執行，且產生的程式碼或其他產物符合版本承諾。
11. **JDK 發行商與完整版本**。專案須記錄實際使用的 JDK 發行商與完整版本。允許多種發行版本時須明訂支援範圍。修補更新或更換發行商時，依影響驗證相容性並保留紀錄，例如啟動參數、外部連線與關鍵流程。
12. **產物與執行環境追溯**。每個發布產物須可追溯實際建置 JDK、編譯目標、依賴版本與相容性驗證紀錄。部署後須能核對產物識別與實際 Java 執行環境，包含發行商、完整版本及相關啟動設定。可沿用專案既有建置與部署紀錄。

## 驗收要求

共同驗收與 Java 語言增量均須經實際採用的 Java 型別、API、版本與框架銜接路徑執行，不因引用共通驗收而略過。依變更影響選擇案例，測試層級及證據依[共通測試策略](../../../quality/testing.md)與[規範驗證](../../../quality/rule-verification.md)。

依本次變更與適用能力執行下列檢查，將結果連到受驗產物及其版本。測試層級與執行門檻依[共通測試策略](../../../quality/testing.md)制定。

### 共同驗收

### Java 語言增量驗收

| Java 條文 | 語言增量驗收 |
| --- | --- |
| <a id="acceptance-java-version-target"></a>1、2 | 核對版本宣告與實際建置設定。以不符合目標版本的語法或標準 API 案例，確認適用檢查會拒絕，並核對產物格式。 |
| <a id="acceptance-java-runtime-matrix"></a>3、4 | 查核各承諾執行版本的實際驗證結果。多模組按依賴關係核對使用端與提供端的相容範圍，不能只依單一較新環境通過推論所有版本符合。 |
| <a id="acceptance-java-version-upgrade"></a>5、6 | 核對實際解析出的直接與間接依賴要求。提高最低版本時檢查使用端影響、遷移順序及回退安排，確認支援範圍變更已有明確決策。 |
| <a id="acceptance-java-api-exceptions"></a>7、8、9 | 依實際使用情形核對 Preview、內部 API、存取放寬與棄用 API 的紀錄。確認適用核准、環境配套、維護責任及重新評估條件，並驗證替代做法符合目標版本。 |
| <a id="acceptance-java-toolchain-compatibility"></a>10、11 | Java 環境或工具變更後，核對必要測試與分析確實執行，避免將被略過的檢查計為通過。確認產生碼與產物仍相容，並保留發行商及完整版本變更的驗證結果。 |
| <a id="acceptance-java-artifact-runtime"></a>12 | 從指定發布產物查回建置環境、編譯目標、依賴與驗證紀錄，再核對部署環境中的實際產物及 Java 環境。 |

無法取得某個承諾版本的執行結果時，須列為尚未驗證，明示缺少的環境或證據。審查與合併條件依[Git、PR 與程式碼審查](../../../workflow/git-pr-review.md)處理。
