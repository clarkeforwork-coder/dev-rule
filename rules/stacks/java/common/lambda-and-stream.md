# Java Lambda 與 Stream

本文件只維護 Java 的具體要求；引用的共通規範同樣具有約束力。

本文件承接[程式碼設計與公開介面](../../../coding/code-design.md)，定義 Java Lambda 與 Stream 的表達、執行及驗收要求。型別標註依[型別宣告與泛型](types-and-generics.md)，集合語意與資料規模依[集合與資料所有權](collections-and-ownership.md)，失敗與資源管理依[例外與資源管理](exceptions-and-resources.md)。

## 表達與狀態管理

1. **意圖與可讀性優先**。依[程式碼設計與公開介面](../../../coding/code-design.md)、[命名與可讀性](../../../coding/naming.md)執行。Java Lambda／Stream 不強制取代迴圈；複雜或獨立責任採具名方法或清楚流程，不要求每個 Lambda 都抽方法。
2. **明確的參數型別**。自行宣告的 Lambda 參數須明確標示型別，不使用省略型別或 `var` 取代。方法參考可在型別契約完整且意圖清楚時使用，不要求機械式改寫成 Lambda；來源集合與相關契約仍須保留泛型資訊。呼叫目標或業務意義不清楚時，使用明確的 Lambda 或具名方法。
3. **中間操作不隱藏業務副作用**。Stream 的篩選、轉換及其他中間操作須避免隱藏業務副作用，`peek` 不得承擔必要業務操作。需要寫入或外部呼叫時，須以責任明確的執行步驟表達，並維持順序、失敗與部分成功保證；使用 `forEach` 也不免除上述責任。
4. **明確累積結果**。Lambda 與 Stream 的結果累積須使用明確的收集、歸約或流程設計，不得隱藏修改外部集合、計數器或旗標來影響元素處理。需要跨元素狀態時，須明確表達順序與管理責任，可使用清楚的迴圈或適當彙整，不為使用 Stream 而隱藏狀態。

## 執行、平行與歸約

5. **延遲與短路範圍**。使用 Stream 時須確認實際執行時機、終端操作與短路範圍，不得把流程建立視為工作完成，也不得假設所有元素都會被處理。契約要求完整驗證或逐項處理時，須選用能維持該保證的明確流程，不把必要工作藏在可能提前停止的操作中。
6. **平行處理的採用條件**。採用平行 Stream 須有明確需求，先驗證資料隔離、順序、歸約與失敗語意，評估執行資源及阻塞影響，並以代表性負載量測確認收益。不得僅因資料量大或改寫方便就啟用平行處理，也不得忽略對其他工作及副作用保證的影響。
7. **歸約與收集契約**。須明訂初始值、累積及合併規則，維持所需的結合性與結果語意。允許平行處理時，分段計算再合併也須符合契約。順序敏感的運算須採用能保留該順序的流程，例如逐步捨入不能任意改變分組。可變容器使用適當的收集機制，不以共用可變初始值造成資料互相污染。

## 失敗、消費範圍與驗證

8. **維持錯誤分類**。Lambda 與 Stream 中的失敗須遵循既有錯誤分類，不得為配合函式介面而吞錯、回傳替代值或默默移除失敗項目。例外傳遞受介面限制時，須明確調整流程或依邊界契約轉換，保留原始原因，不以隱藏拋出或任意轉換規避要求。允許部分成功時，保留各筆結果與對應關係；技術故障仍依既有例外契約處理。
9. **明確消費範圍**。Stream 須有明確的消費範圍，不得在消費後重用，也不得讓多個流程共用同一實例各自消費。需要重複處理時，須明確選擇範圍受控的快照或重新取得資料，並定義一致性與資源生命週期。提供者能重新取得 Stream 不代表結果必定相同；涉及外部資源時，仍須明訂有效期與關閉責任。
10. **執行語意驗收**。Lambda 或 Stream 流程新增及變更時，須依影響驗證資料邊界、執行與短路範圍、順序、歸約、失敗及適用的資源保證。平行處理另須驗證隔離與實際效能，不僅確認一般案例的最終結果相同。不重測 Stream 函式庫本身，也不要求每段簡單轉換測試全部情境。

例如參數明確的 Lambda 與意圖清楚的方法參考，均可用於已具完整泛型資訊的來源：

```java
orders.stream().filter((Order order) -> order.isCancellable());
orders.stream().filter(Order::isCancellable);
```

上述片段僅示範篩選條件的表達，尚未消費結果，不代表已完成驗證或執行取消操作。

數值歸約涉及精度與捨入時依[數值、日期時間與文字處理](numbers-dates-text.md)；平行處理的量測依[效能與資源使用](../../../quality/performance.md)。

## 驗收要求

共同驗收與 Java 語言增量均須經實際採用的 Java 型別、API、版本與框架銜接路徑執行，不因引用共通驗收而略過。依變更影響選擇案例，測試層級及證據依[共通測試策略](../../../quality/testing.md)與[規範驗證](../../../quality/rule-verification.md)。
