# Java 反射、動態能力與檢查抑制

本文件只維護 Java 的具體要求；引用的共通規範同樣具有約束力。條號保留供既有決策與驗收追蹤，不代表引用條目另有一套政策。

本文件承接[型別安全](../../../coding/type-safety.md)及[規範治理](../../../workflow/rule-governance.md)，定義動態能力、特殊存取與檢查抑制的限制。手寫整合與測試程式碼適用相同要求，工具限制不構成自動例外。Java 型別要求另依[型別宣告與泛型](types-and-generics.md)，JDK 內部 API 與存取放寬另依[版本要求](version-policy.md)。

## 動態能力與存取邊界

1. **明確需求與型別契約**。反射與動態呼叫須有明確需求，已知的業務能力優先透過靜態型別契約表達。必要動態能力須集中於責任明確的元件，限制影響範圍並提供具型別的內部契約，不得藉此繞過型別安全要求。框架整合、外掛或通用工具的動態名稱與未知物件不得任意散入業務流程。
2. **受控目標與授權**。依[受控目標與授權的共通要求](../../../quality/security.md#rf-02)執行。Java 類別、方法及建構子的動態目標須受控，不因型別符合就略過授權。
3. **維持封裝與不變條件**。反射與動態能力不得繞過可見性設計、建立驗證或業務不變條件。需要特殊存取時，優先採用受支援的整合方式；必要的存取放寬須個別核准並驗證影響，不得以框架、映射或測試用途自行豁免。例如不能以直接寫入私有欄位避開正式建立規則。
4. **使用前驗證契約**。依[使用前驗證契約的共通要求](../../../coding/type-safety.md#rf-04)執行。Java 動態元件須驗證能力、版本及型別，不只確認名稱存在，也不靠未驗證轉型掩蓋不相容。
5. **區分故障與執行結果**。依[區分故障與執行結果的共通要求](../../../coding/error-handling.md#rf-05)執行。Java 反射或動態呼叫的外層例外須保留原始原因，不能據此推定目標未執行而替換或重跑。

## 檢查抑制與產生碼

6. **限定檢查抑制**。依[限定檢查抑制的共通要求](../../../workflow/rule-governance.md#rf-06)執行。Java `@SuppressWarnings` 須限具體規則及最小範圍；raw type／unchecked 仍遵守型別與泛型規範的禁止事項及個別核准要求。
7. **產生碼不擴大豁免**。依[產生碼不擴大豁免的共通要求](../../../workflow/rule-governance.md#rf-07)執行。Java 產生碼須由來源／設定重建；手寫銜接維持完整型別檢查，重建後確認例外範圍仍適用。
8. **驗證限制實際有效**。依[驗證限制實際有效的共通要求](../../../quality/rule-verification.md#rf-08)執行。Java 實際反射、存取及重新產生路徑依下方驗收，不只確認警告消失或成功目標能執行。

目標與操作權限另依[安全規範](../../../quality/security.md)，動態呼叫的失敗傳遞依[例外與資源管理](exceptions-and-resources.md)。建立與還原仍須遵守[類別、介面與物件建立](classes-and-construction.md)及[值物件規範](value-objects.md)。

## 驗收要求

下表保留原決策編號與 Java 實作案例。共通原則依各條連結的主要來源及其驗收執行；Java 型別、API、版本與實際框架銜接路徑仍須完成下列適用驗收，不因原則提升而略過。

依變更影響選擇案例，沿用[共通測試策略](../../../quality/testing.md)及[規範驗證](../../../quality/rule-verification.md)。

| 對應決策 | 驗收內容 |
| --- | --- |
| 1、2 | 審查動態能力的必要性、管理位置與內部型別契約。驗證允許目標可依權限執行，未登錄或未知目標明確拒絕；已知且型別符合的目標仍須通過授權，拒絕時沒有不應發生的副作用。 |
| 3、4 | 以合法及不相容目標驗證註冊、啟動或執行前檢查；確認能力、版本、參數與結果型別符合所需契約。核對特殊存取的核准範圍，以及建立與還原不會繞過必要驗證或產出無效物件。 |
| 5 | 分別觸發適用的解析、存取、契約及目標執行故障，確認原因與分類保留，未將已執行的故障誤當未找到目標，且未進行無安全依據的替換或重跑。 |
| 6 | 核對抑制規則、最小範圍、判定依據及適用核准。以代表性檢查案例確認範圍外仍受檢查，沒有因抑制一項問題而關閉整個類別、模組或專案的必要檢查。 |
| 7 | 依實際來源與設定重新產生，確認產出及例外範圍可重現，手寫銜接仍符合型別契約。工具或產生器更新時，重新確認例外依據，未沿用已失效的抑制。 |
| 8 | 確認驗收包含成功與拒絕、故障及限制生效的證據，不以警告消失或合法目標成功作為全部符合的依據。 |

偏離禁止事項須依[例外核准流程](../../../workflow/rule-governance.md#例外核准)取得明確決策，不因工具限制自行放寬，也不得將核准擴及其他位置。
