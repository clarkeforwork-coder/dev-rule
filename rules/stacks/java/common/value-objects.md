# Java 專屬值型別與領域值物件

本文件只維護 Java 的具體要求；引用的共通規範同樣具有約束力。條號保留供既有決策與驗收追蹤，不代表引用條目另有一套政策。

本文件承接[領域建模](../../../coding/domain-modeling.md)，適用於 Java 專屬值型別與領域值物件。型別使用與空值處理另依[型別宣告與泛型](types-and-generics.md)及[null 與 Optional](null-and-optional.md)。具有身分與生命週期的 Entity，其狀態變更另依業務規則管理，不因本文件而要求所有 Entity 不可變。

## 型別責任與有效性

1. **建立專屬型別的條件**。依[領域建模](../../../coding/domain-modeling.md)執行。Java 的 `OrderId` 與 `CustomerId` 須維持不同業務型別；一般描述性資料不要求機械式包裝。
2. **建立時保護不變條件**。依[領域建模](../../../coding/domain-modeling.md)、[資料驗證](../../../coding/validation.md)執行。Java 建構子或工廠維持一致驗證；合法 `OrderId` 不代表訂單存在或已取得存取權。
3. **不可變性**。依[不可變性的共通要求](../../../coding/domain-modeling.md#vo-03)執行。Java 欄位標示 `final` 不代表內容不可變；傳入及取出可變集合或巢狀物件時，須以不可變表示、封裝或必要的防禦性複製維持隔離。

## 相等性、正規化與運算

4. **值相等的條件**。須明訂相等條件，並維持 `equals()` 與 `hashCode()` 一致，相等物件須具有相同雜湊值。相等性須保留業務概念的區別，不得只比較底層值或物件身分，也不得未經確認就採用自動產生的相等性。例如不同實例的相同訂單識別碼可相等，但相同數字的 `OrderId` 與 `CustomerId` 不應相等；金額相同而幣別不同也不應視為相等。
5. **正規化規則**。依[正規化規則的共通要求](../../../coding/domain-modeling.md#vo-05)執行。Java 建構子、工廠及其他建立入口須一致執行正規化，並讓 `equals()` 與 `hashCode()` 反映已定義的值語意。
6. **運算責任**。依[運算責任的共通要求](../../../coding/domain-modeling.md#vo-06)執行。Java 值物件操作保留專屬型別；必要邊界呈現可讀底層值，跨幣別等依賴外部政策的操作由領域元件協調。

## 還原、實作形式與對外表示

7. **資料還原**。依[資料還原的共通要求](../../../coding/domain-modeling.md#vo-07)執行。Java 建構、反序列化及持久化還原均須維持共同保證；一般類別或 `record` 的實作選擇不得形成驗證旁路。具體框架配置另訂。
8. **一般類別與 record**。可依支援的 Java 版本與業務需求，選用一般類別或 `record`，不強制所有值物件採用相同形式。選擇須符合驗證、不可變性與相等性要求，並檢視自動產生的方法是否適合公開，不因採用特定語法就視為符合規範。可變內容仍須保護，敏感值不得因自動產生字串表示而洩漏。語言功能另依[版本要求](version-policy.md)。
9. **診斷字串與交換格式**。值物件的診斷字串與持久化、傳輸格式須分別定義，不得默認以 `toString()` 作為穩定的資料交換契約。對外表示須遵守格式、相容性與敏感資料揭露要求，不能因值被包成物件就允許輸出原值。
10. **業務保證的測試**。依[領域建模](../../../coding/domain-modeling.md)、[共通測試策略](../../../quality/testing.md)執行。Java 的 `equals()`、`hashCode()`、`record` 自動產生方法與還原路徑依下方驗收表驗證，不機械式測試每個產生的方法。

映射與歷史資料處理另見[資料映射](../../../architecture/data-mapping.md)及[資料遷移](../../../data/migrations.md)；敏感資料與診斷輸出依[安全規範](../../../quality/security.md)及[日誌、稽核與可觀測性](../../../quality/observability.md)。

## 驗收要求

下表保留原決策編號與 Java 實作案例。共通原則依各條連結的主要來源及其驗收執行；Java 型別、API、版本與實際框架銜接路徑仍須完成下列適用驗收，不因原則提升而略過。

依受影響的值型別與實際使用路徑選擇案例，沿用[共通測試策略](../../../quality/testing.md)與[規範驗證](../../../quality/rule-verification.md)。

| 對應決策 | 驗收內容 |
| --- | --- |
| 1、2 | 審查專屬型別能否阻止業務概念混用，相關介面有無退回一般字串或數字。驗證合法值、邊界值及不合法值，確認建立成功後符合自身規則，且未將格式有效誤當成存在性或授權成立。 |
| 3 | 對含可變資料的型別，修改傳入或取出的資料，確認原值物件未受影響。檢查封裝與必要的複製，不能只檢查欄位是否為 `final`。 |
| 4 | 驗證不同實例的相等值及具代表性的不相等值，相等物件的雜湊值須相同。適用時確認作為集合元素或映射鍵的行為符合契約，不要求不相等物件一定具有不同雜湊值。 |
| 5 | 以不同合法表示及不合法輸入驗證正規化、驗證順序與相等性符合契約，所有建立入口結果一致，沒有未授權的修剪或數值修正。 |
| 6 | 驗證適用運算的結果、單位與有效性限制，原物件維持不變。確認不相容的值依契約拒絕或處理，使用端未各自拆值繞過規則。 |
| 7 | 經實際採用的反序列化、持久化或框架映射路徑驗證合法與不合法資料。涉及歷史資料時，確認按明訂版本或遷移規則還原，不產出違反契約的物件。 |
| 8、9 | 核對實作形式符合支援版本，產生的方法與手寫方法均遵循相等性、不可變性及揭露契約。確認診斷字串未被默認當成交換格式，對外映射符合約定且未洩漏敏感值。 |
| 10 | 核對測試涵蓋受影響的業務保證與失效邊界，不以只有建立成功的案例代替驗收，也不要求無業務邏輯的存取方法逐一測試。 |

既有程式碼與必要例外依[規範治理](../../../workflow/rule-governance.md)辦理，不因工具或框架產生物件而自行豁免。
