# 規範驗證

各主題的必測情境與審查項目列於下文。選擇測試層級、安排執行門檻及維護案例時，依[共通測試策略](testing.md)辦理。

## 共同把關

- 可由工具判斷的要求，必須使用適用的編譯器、靜態分析、Lint 或架構檢查執行，例如明確型別宣告、不安全轉型與依賴限制。
- 型別與其他已配置的強制檢查納入 CI，違規時阻擋合併；核准例外與既有違規依[規範治理](../workflow/rule-governance.md)精確管理。
- 行為測試驗證錯誤輸入拒絕、資料轉換、空值語意、業務條件，以及 Response 不含敏感欄位等實際行為。
- 需要理解業務語意的要求，必須人工審查，例如物件拆分是否合理、專屬型別是否表達正確概念。
- 工具尚未涵蓋的要求必須列入審查清單，不能因 CI 通過就視為全部符合。

驗收時須逐項核對必要規範與自動檢查、行為測試或人工審查的對應；工具未覆蓋的必要內容有明確清單及處置，不以 CI 成功代替完整性確認。

## 架構檢查與可測試性

- 可自動判斷的架構依賴限制必須納入 CI，包括引用其他模組內部元件、禁止的跨層依賴、循環依賴、核心引用架構禁止的技術實作，以及共用元件反向依賴業務模組。
- 業務責任是否合理、模組是否應拆分等語意問題由人工審查，不只依靠工具。
- 微服務實際呼叫鏈須搭配整合驗證與執行期追蹤，不能只靠程式碼依賴分析判斷同步呼叫循環。
- 核心業務規則必須能在不啟動完整系統、不連線真實資料庫或第三方服務的情況下獨立驗證。
- 純計算、狀態判斷與業務限制可直接建立物件測試；外部能力透過明確依賴提供測試替身，不因此強制每個類別建立介面。
- 資料存取、框架設定與第三方整合以適當整合測試確認；跨模組流程也必須有適當整合驗證，不得只憑替身測試認定整體正確。
- 工具依專案選擇，既有違規沿用漸進導入機制。

介面用途的驗收見[介面用途驗收](../architecture/dependency-composition.md#acceptance-interface-purpose)。

## 錯誤處理驗證與驗收

依操作風險、實際邊界、副作用與重要業務流程，驗證[錯誤處理](../coding/error-handling.md)的適用失敗路徑，不只測試成功流程，也不要求每個函式套用所有故障情境。

- 預期業務失敗回傳正確結果，技術故障與程式缺陷不被誤分類或吞掉。
- 逾時、結果未知與取消不被誤報為成功或確定失敗。
- 部分成功、降級與補償失敗符合契約，不隱藏未完成事項。
- 必要資源確實釋放，原始錯誤未被清理錯誤覆蓋。
- 對外回應不洩漏敏感資訊，內部保留必要診斷資訊。

| 契約 | 驗收內容 |
| --- | --- |
| <a id="acceptance-partial-operation"></a>[多步驟與部分成功](../coding/error-handling.md#多步驟與部分成功) | 在處理中途製造適用的失敗，核對實際狀態是否符合全部成功或部分成功保證；允許部分成功時，結果須能對應已完成、未完成或結果未知的項目，不隱藏項目失敗或未完成事項。集合批次修改適用同一驗收。 |

測試程式碼同樣遵守下列型別安全要求。

## 補償流程驗收

依[跨步驟失敗與業務補償](../workflow/compensation.md)，按失敗影響選擇案例，從擁有業務狀態的模組核對效果，並比對使用者可見的結果與未決事項。

- 模擬部分成功後發生其他合法變更，確認補償只消除原操作指定的效果，相依步驟等前置條件成立後才執行。
- 模擬原操作結果未知及請求遲到，驗證流程會等待核對，或在允許發起補償的情境下，交換到達順序仍得到約定結果。
- 例如退款已完成但回應遺失時，讓流程重啟並核對付款紀錄。確認同一退款重送或併發只退一次、已完成的庫存釋放仍正確，且對外能區分訂單未成立與退款已完成。
- 模擬補償持續失敗，確認達到停止條件後停止自動重試，接手者能查回必要資訊，案件在符合業務結案條件前保持未決。

- 核對不可撤銷步驟的執行前提與後續失敗處置，確認符合業務約定。對同一原操作的不同合法補償，驗證各自識別可區分，例如兩筆等額部分退款均可完成，而各自重送仍維持一次效果。

## 外部整合與事件故障恢復驗證

依實際採用的機制與風險，驗證[外部整合](../interfaces/external-services.md)與[事件流程](../interfaces/events.md)中斷後能否恢復，以及恢復是否重複產生副作用。適用情境包括：

- 外部呼叫逾時、限流或持續故障下，重試、整體期限與熔斷是否符合設定。
- 業務資料提交後、事件發布前中斷，恢復後是否仍能送出。
- 消費端業務完成後、確認前中斷，重送是否避免重複副作用。
- 重複、亂序、缺漏與不支援版本是否依契約處理。
- 死信重新處理、歷史重播與即時事件交錯是否維持正確結果。
- 來源驗證失敗或積壓超標是否阻止不當處理並觸發必要通知。

可使用受控環境與故障模擬，不要求在正式環境製造故障，也不要求每個整合套用全部情境。測試替身無法證明的訊息或交易保證，必須以適當整合測試驗證。

## 資料庫行為與遷移驗證

涉及[資料約束與查詢](../data/persistence.md)、[交易與鎖定](../data/transactions.md)的保證，必須以與正式環境相容的實際資料庫行為驗證，不能只靠 Mock 或記憶體替代品判定正確，不要求連線正式資料庫。

- 驗證併發修改能保護業務條件，以及衝突、死鎖與逾時是否依策略處理。
- 驗證唯一性等約束、交易回滾與錯誤轉換。
- [資料遷移](../data/migrations.md)使用具有代表性的既有資料驗證，包含新舊版本相容及適用的失敗恢復情境。
- 大量操作依風險驗證分批、安全續跑與結果核對。
- 依專案實際使用的能力選擇測試，不要求每個資料存取方法套用全部情境。

## API 契約與操作驗證

依[API 操作語意與介面設計](../interfaces/api-contracts.md)，以契約測試或整合測試確認公開契約、範例與實際行為一致。

- 驗證正常操作的必要輸入、預期輸出與業務效果，不只確認欄位型別。
- 依操作風險與語意選擇重要情境，例如對象不存在、集合無結果、版本衝突、完整替換與部分修改、重複刪除及非同步完成程度。
- 確認查詢沒有隱藏業務副作用，更新與刪除不繞過業務條件，身分與管理欄位不受未授權輸入控制。
- 確認適用的傳輸格式保留必要精度與範圍，以及同一業務能力在不同入口維持一致的規則與結果語意。
- 不要求每個 API 套用全部情境；範例不得包含真實秘密或敏感資料。
- 範例與測試引用既有契約來源，不建立另一套獨立定義；變更時同步更新文件、範例與測試。

### API 版本相容性與遷移驗收

依[API 版本管理、淘汰與使用端遷移](../interfaces/api-versioning.md)，將提供方的契約驗證與使用端的遷移驗收分開確認。

- 驗證明確指定與省略版本的請求均依契約處理。對未知版本或仍可接收請求的停用入口，確認回傳可辨識的錯誤，且未執行新版操作。
- 對共用實作或修補所影響的每個受支援版本，驗證輸入、輸出與可觀察的業務效果。例如舊版取消訂單承諾同步完成時，收到成功回應後應能查到已取消。新版若只承諾已受理，則須驗證使用端能追蹤最終結果。
- 關鍵流程在切換前以代表性資料驗證成功、失敗、處理中及適用的恢復路徑，涵蓋新版寫入的狀態與尚未完成的操作。正式切換後，由使用端負責人核對業務結果。
- 停用審查核對公告日期、關鍵使用端遷移紀錄及涵蓋低頻操作的實際用量。仍有使用或狀態未確認時，檢查負責人是否記錄影響與處置決策。

### 列表查詢組合驗證

依 API 支援的能力與風險，驗證[列表查詢契約](../interfaces/list-queries.md)在分頁、篩選與排序組合使用時的行為。

- 驗證空結果、最後一頁（含剛好滿頁）、無效參數與超限筆數。多筆資料的排序值相同時，確認跨頁順序符合契約。
- 以過期、遭修改及與目前查詢條件不符的游標續查，確認回報契約定義的錯誤。
- 在兩次取頁間新增、修改或刪除資料，依契約宣告的一致性判定結果。若承諾快照，須驗證對該快照的遍歷完整且無重複。
- 驗證篩選、排序、續查及總數均維持授權與租戶隔離。測試合法參數組合接近及超出複雜度上限時的行為，確認資源限制有效。

## 公開事件的契約驗證

每種公開事件至少有一個有效範例。發布方與消費方的測試須依[事件命名與內容設計](../interfaces/event-contracts.md)引用同一份契約，並分別驗證以下行為。

- 發布方驗證觸發條件與實際產出。例如先把地址從 A 改成 B，再提交一次 B，只有第一次成立「地址已變更」。驗證事件來源、識別、必要欄位組合，以及內容限於契約用途和訂閱者權限。
- 消費方驗證有效範例會產生契約預期的結果，條件式必填欄位缺漏時能依規定處理。測試資料使用虛構值。
- 依支援範圍與風險，以舊版範例驗證重播後的歷史語意，以原事件與更正事件驗證亂序、重複及完整重播的結果。傳送或代送後須仍可辨識原事實，避免重複副作用。
- 變更公開契約時，檢視發布方、消費方、範例及測試是否同步更新。訊息傳送與恢復的驗證另依[事件可靠性](../interfaces/events.md)。

## 安全驗收

依各能力的失敗後果與入口，選擇接近合法操作的越權案例，同時驗證拒絕結果、對外揭露與實際副作用。測試資料、憑據與目的地須依[共通測試策略](testing.md)隔離，預期行為以[安全共通規範](security.md)為準。

- 例如具備 A 門市退款權的客服提交 B 門市訂單時，確認該操作遭拒、回應未違反訂單存在性揭露政策、訂單及帳務未變更，且未送出退款請求。對允許部分成功的批次，分別核對獲准與越權項目的效果。
- 依功能涵蓋跨租戶、集合計數、可讀不可寫欄位、自行核准、代理執行與排程執行前撤權。對可能繞過共同檢查的 API、背景或事件入口，驗證相同的權限邊界。
- 核對授權服務故障時安全停止、舊工作階段與權杖按時失效、停用後不能續期、併發提交的一次性憑據僅成功一次，以及跨入口無法繞過嘗試與發送限制。
- 依適用情境驗證秘密輪替後的失效與服務恢復、敏感資料副本清除與備份還原，以及惡意輸入、檔案、重新導向與未知反序列化類型能在產生副作用前受到限制。對瀏覽器入口分別驗證未授權的跨來源讀取與跨站狀態變更。

## 可觀測性驗收

關鍵流程上線前，以及調整欄位、收集管線、告警路由或門檻後，須依風險在受控環境驗證受影響的流程。例如模擬退款已受理而背景工作停止處理，依[日誌、稽核與可觀測性](observability.md)檢查下列結果。

- 從操作 ID 串回原請求及背景工作，能辨識最後完成的步驟。檢查實際寫出的紀錄，包含框架與 SDK 路徑，確認欄位正確且未寫出禁止的敏感資訊。
- 稽核可還原當時授權依據及已受理狀態。收集端離線後可恢復傳送，診斷抽樣不影響必要事件。業務恢復後追加核對結果，保留原始歷程。
- 確認積壓或等待時間超標時通知實際送達指定測試接收端，無人接手或影響擴大時會升級。停止回報須顯示未知，既有告警持續追蹤，直到業務恢復條件成立才解除。

## 效能與資源驗收

依[效能與資源使用](performance.md)，在上線前針對變更影響的操作與共用資源選擇案例。

- 記錄比較版本、負載、資料分布、環境差異與指標口徑，使量測可以重現。例如 1,000 筆有效查詢中有 940 筆在期限內成功、40 筆較晚成功、20 筆逾時，期限內成功比例應為 94%。分別判讀業務門檻與相對基準的變化，符合複測條件時依約複測。
- 同時施加關鍵與背景工作負載，核對單次用量、總占用及關鍵操作的成功率與延遲。達到執行和排隊上限時，分別核對回覆、實際受理結果與逾期處置。模擬取消或逾時，確認工作依契約停止或繼續，且名額隨實際資源釋放而回收。
- 對有累積風險的流程，持續觀察資源占用、佇列深度或最舊工作的等待時間。若允許尖峰積壓，降低負載後核對恢復所需時間。另依實測用量、成長趨勢及容量調整所需時間，檢查是否已達容量重估條件。
- 對效能改善，核對變更前後的量測結果及受影響的業務行為。例如以快取降低延遲時，須同時驗證快取命中後仍符合授權與資料新鮮度契約。

## 設定管理驗收

依[設定管理與環境差異](../workflow/configuration.md)，分別驗證程式的設定入口與每次部署實際使用的設定。

- 設定契約變更時，須透過實際設定入口自動測試受影響的生效與拒絕情境。例如以不同來源驗證覆寫順序，以拼錯的名稱、無效值或同層衝突驗證拒絕結果。使用虛構敏感值時，核對診斷輸出未帶出原值。
- 支援執行中更新時，先載入有效設定，再送入組合不合法的新設定，從使用處確認整組仍維持原值。變更失聯策略時，驗證允許沿用的期限、重試不延長期限及到期停止的操作。
- 每次部署須驗證待部署版本能接受目標環境合併後的設定。驗證失敗的新實例不得開始處理工作。分階段啟用或回退時，核對實例生效版本與相容條件。移除設定前，確認執行中與可能回退的版本均已解除依賴。

- 更新會影響進行中的操作時，驗證沿用舊設定或重新確認新設定的行為符合契約。跨實例或服務切換時，核對啟用前提已成立。
- 審查暫時性功能開關的負責人、檢視時間與清理條件。保留或移除時，核對延期理由或相容遷移順序。

## 依賴管理驗收

依[第三方套件與依賴管理](../workflow/dependencies.md)，按變更類型核對下列結果。

- 引入或升級時，比對依賴宣告與實際解析差異。核對新套件的來源、用途、授權義務、維護責任，以及腳本可取得的權限。以專案實際使用的功能驗證受影響行為。
- 核對 CI 與發布建置使用同一份鎖定紀錄。驗證內容不符時會停止使用，限定來源缺少指定版本時也會停止安裝。移除依賴後，在乾淨環境驗證相關流程，包含透過設定載入的外掛。
- 從指定發布版本查回產物實際隨附的依賴與補丁，核對安全修補是否進入該產物。疑似竄改時，另查建置期間曾執行的腳本與當時可存取的憑據，確認恢復發布的條件已成立。
- 對仍未修補的漏洞，核對影響判定、負責人與期限。若採暫時措施，須逐一核對可觸發漏洞的入口，驗證措施的實際涵蓋範圍，並核對剩餘風險的例外核准範圍與有效期。

- 共用函式庫須核對支援範圍與可重現的測試版本組合。檢視維護狀態或自行修補版本時，確認重新評估、替換或移除補丁的條件及負責人。

## Git 與 PR 驗收

依[Git、PR 與程式碼審查](../workflow/git-pr-review.md)，在合併前核對審查與驗證證據是否涵蓋實際變更。

- 檢查 PR 目的、實際差異與影響範圍是否一致，相關測試與文件是否同步。確認作者已自查，驗證結果可對應到版本，未驗證事項及相容、設定、遷移安排均已揭露。
- 核對必要審查者的資格與核准結果，確認阻擋合併的問題已處理、歧見已有決策依據。核准後新增修改或解決衝突時，依影響補做審查與驗證。
- 確認必要檢查已成功完成且適用於實際整合內容。核對分支寫入限制涵蓋人工及自動化操作，任何繞過均有適用的例外紀錄。已分享分支改寫時，核對事前協調及遠端變更的處理結果。
- 對照變更目的檢查測試斷言。修正可重現缺陷時，確認回歸案例能暴露原問題。例如重送同一退款請求後，須核對實際退款次數。AI 或工具提供的結果也須有實際執行證據。
- 確認合併提交可追溯到 PR、審查與驗證。回退須核對後續依賴及相容性，跨分支修正須逐一追蹤結果。緊急變更的待補項目須有負責人與期限，後續結果及處置連回原 PR。

<a id="語言與新增共通主題驗收入口"></a>

## 語言與共通主題驗收入口

Java 的版本、型別、標準 API 與執行模型驗收集中於[Java 語言索引](../stacks/java/README.md#驗收入口)，不在共通文件重複維護各主題摘要。其他語言依其適用規範補足；共同要求的效力依[規範索引](../README.md#規範效力)。

共通主題的具體驗收見[集合與資料所有權](../coding/collections-and-ownership.md#驗收要求)、[資源生命週期](../coding/resource-lifecycle.md#驗收要求)、[併發與非同步](../coding/concurrency-and-async.md#驗收要求)及[數值、日期時間與文字](../coding/numbers-dates-text.md#驗收要求)。領域、映射、空值與介面等補充契約的驗收由各自主要文件維護。

## 測試程式碼

- 自行撰寫的測試程式碼必須遵守相同型別安全規範，包括明確宣告、禁止型別逃逸與使用正確專屬型別。
- 測試不合法外部資料時，在接收邊界使用原始 JSON、字串或位元組等輸入。
- 測試專屬型別驗證時，傳入不合法原始值並確認建立失敗，不透過繞過型別檢查偽造有效的內部物件。
- 測試替身必須符合被替代介面的型別契約。

## 審查清單

依[命名與可讀性](../coding/naming.md)及[程式碼設計與公開介面](../coding/code-design.md)，在實際呼叫處檢查：

- 名稱與參數能否表達領域語意、操作效果與單位？布林名稱是否準確說明成立條件，字面值是否由對應規則管理？
- 函式是否保留清楚的流程入口，並將各自變動的規則交給所屬元件？參數型別是否排除無效組合？
- 可見性與修改權是否限於必要範圍？呼叫端能否經由唯讀介面取得可修改的內部資料？
- 註解的理由與依據是否仍有效？呼叫者能否從公開契約得知適用的前置條件、完成效果、失敗與重試保證？

其他共通要求：

- 邊界、物件拆分與轉換責任是否符合專案架構？
- 是否只傳遞必要欄位，且未暴露內部模型或第三方契約型別？
- 型別是否明確，專屬型別與泛型是否有實際保障？
- 未知輸入、缺值、清空與狀態是否得到正確驗證與表達？
- 契約變更是否評估所有使用端，並安排必要的相容措施？
- API 是否表達明確業務意圖與成功保證，更新、刪除及不存在語意是否清楚？
- API 命名、可信欄位、傳輸格式與多入口行為是否一致，是否有可驗證且同步維護的範例？
- 共用型別是否有管理責任，依賴方向是否正確？
- 模組公開入口是否符合團隊慣例，業務規則與資料是否有明確歸屬？
- 跨模組流程、查詢與交易是否遵守責任邊界，各入口是否均執行必要業務檢查？
- 依賴是否明確組裝，核心規則是否能獨立驗證？
- 架構約束變更是否經確認，並同步更新文件與檢查？
- 錯誤分類、捕捉與記錄責任是否明確，降級、未知結果、取消與部分成功是否依契約處理？
- 清理或補償失敗是否保留原始原因與後續責任，適用失敗路徑是否完成驗證？
- 重試是否有單一管理位置、安全依據與整體期限，冪等是否涵蓋併發及保留期限？
- 事件發布、消費確認、隔離與重播是否可恢復，並維持順序與副作用安全？
- 非同步完成依據、逾期核對、來源驗證與積壓處理是否有明確機制及責任？
- 新增與修改部分是否符合規範，偏離是否已有有效核准？
- 併發更新、隔離、鎖定與資料庫約束是否能保障業務條件，衝突及重試是否安全？
- 查詢是否有界，副本與快取是否符合讀取一致性需求，效能改善是否保留授權與隔離？
- 遷移是否版本化且維持所需相容性，大量操作是否可恢復並核對結果？

## 動態限制與文件驗證

<a id="dynamic-control-verification"></a>
<a id="rf-08"></a>

### 驗證限制實際有效

動態能力、特殊存取或檢查抑制新增及變更時，須驗證允許與拒絕路徑、故障分類、必要不變條件及檢查範圍。涉及工具產出時，須驗證實際重新產生的結果，不僅測試成功案例或確認警告消失。

<a id="document-verification"></a>
<a id="nd-07"></a>

### 形式與語意分別驗收

命名與文件變更須以自動檢查維持可判定的形式要求，並由人工審查語意、責任及契約一致性。相關連結、參照與範例須依影響驗證；具有可執行意義的範例須確認能在適用環境下使用。不以格式通過或文件成功產生代替內容正確性，也不強制所有方法填寫相同文件內容。

## 補充契約驗收

依變更影響及實際採用能力驗證，測試層級與案例維護依[共通測試策略](testing.md)；不要求每個操作涵蓋全部情境，也不重測語言標準函式庫本身。

| 契約 | 驗收內容 |
| --- | --- |
| <a id="acceptance-dynamic-controls"></a>[驗證限制實際有效](#dynamic-control-verification) | 確認驗收包含成功與拒絕、故障及限制生效的證據，不以警告消失或合法目標成功作為全部符合的依據。 |
| <a id="acceptance-document-verification"></a>[形式與語意分別驗收](#document-verification) | 驗證受影響的連結、文件參照與適用範例，確認在適用環境下可用。保留語意與契約審查，不把格式或文件產生成功當成全部符合。 |

<a id="reproducible-check-configuration"></a>
<a id="au-02"></a>

## 檢查配置可重現

必要檢查的工具版本、規則及設定須受版本控制。本機與 CI 使用一致規則，提供可重現的執行方式，不只依賴 IDE 個人設定。具體工具由專案選擇；語言規範補充必要能力。

<a id="acceptance-check-configuration"></a>

驗收：在依專案文件建立的環境執行同一入口，核對版本、規則及設定一致；確認不是只有 IDE 能執行。

<a id="actual-check-scope"></a>
<a id="au-03"></a>

## 實際執行範圍

必要檢查須核對實際執行範圍與結果，包含適用的模組、程式碼及測試範圍。未執行、被略過或未涵蓋必要內容不得視為通過；無適用內容須有明確依據，不能僅以零問題或成功退出判定有效。

<a id="acceptance-check-execution"></a>

驗收：以實際執行紀錄核對必要範圍，辨識略過、未收集測試及排除內容；無適用內容的判斷可追查。

<a id="check-configuration-validation"></a>
<a id="au-04"></a>

## 檢查設定本身的有效性

新增或變更檢查規則、範圍及配置時，須以代表性的符合與違反案例確認可以正確放行及拒絕。不能只確認工具啟動、報告產生或警告消失，也不要求每個 PR 重測全部檢查工具。

驗收：代表性正例通過、反例被適用規則拒絕，並確認排除或抑制沒有擴大到其他必要範圍。

<a id="evidence-version-validity"></a>
<a id="au-06"></a>

## 證據版本與快取有效性

檢查與測試證據須對應實際受驗版本、環境及規則設定。使用快取或增量結果時，須確認相關輸入、依賴及必要涵蓋範圍仍有效；無法確認時重新執行受影響檢查，不把舊結果直接套用到新內容。合併前另核對與目標分支整合後的適用性。

驗收：從結果追溯程式版本、工具／規則設定及環境；改變受影響輸入或依賴時，確認快取失效或有可核對的有效性依據。

<a id="diagnostic-classification"></a>
<a id="au-08"></a>

## 結果分類與安全診斷

檢查及測試結果須可定位、可重現並追溯受驗版本，區分程式違規、行為失敗與工具故障。工具無法執行或解析不代表程式通過；診斷資訊遵守安全及日誌規範，不輸出秘密或不必要的敏感資料。

驗收：分別核對違規、測試失敗與工具故障的結果及處置；確認定位與重現資料足夠且經安全檢查。

<a id="effective-merge-gates"></a>
<a id="au-09"></a>

## 合併門檻實際有效

必要檢查的合併阻擋須實際生效。檢查配置或合併保護新增及變更時，確認失敗、未完成或應執行卻被略過的變更無法直接合併，不能以只產生報告取代門檻。可使用測試分支、測試儲存庫或平台檢查能力，不要求每個 PR 故意製造失敗。核准例外依既有流程追溯。

驗收：以受控方式確認不符合條件會阻擋，符合條件可依程序合併，涵蓋人工與自動化操作；例外具核准及紀錄。

違規基準依[精確違規基準](../workflow/rule-governance.md#precise-violation-baseline)，自動修正依[自動修正的審查](../workflow/git-pr-review.md#automated-fix-review)。檢查抑制與產生碼依[規範治理](../workflow/rule-governance.md)，診斷遵守[安全](security.md)及[可觀測性](observability.md)。
