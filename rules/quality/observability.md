# 日誌、稽核與可觀測性

診斷日誌供工程人員追查執行過程與故障。業務稽核供查核者還原操作、授權與當時的結果。兩者可共用平台及操作識別碼，但必要稽核事件必須依業務條件記錄，包含適用的成功操作。調整診斷層級或抽樣率不得影響這項保證。

<a id="diagnostic-logging-and-tracing"></a>
## 診斷日誌與追蹤

專案統一依操作結果及影響判定層級，具體名稱依工具對應。由負責判定結果的元件記錄故障，避免逐層重複記錄。責任分工見[錯誤處理](../coding/error-handling.md#failure-logging)。

| 層級 | 判定依據與範例 |
| --- | --- |
| DEBUG | 排查所需的執行細節，例如一次重試的等待時間。 |
| INFO | 值得保留的正常運作事件，例如背景工作完成。 |
| WARN | 操作依契約完成，但有需留意的異常，例如主要來源故障而使用允許的快取。 |
| ERROR | 技術故障使本次操作無法依契約完成。預期的庫存不足等業務結果不得僅因遭拒就列為系統錯誤。 |

- 每筆診斷日誌須可取得事件時間、層級、服務或元件名稱及穩定的事件名稱。環境可由平台補上。有請求或背景工作脈絡時，附上可用的追蹤或操作識別碼。依事件用途加入耗時、重試次數或錯誤代碼，專案統一欄位名稱、型別與單位。
- 同步呼叫傳遞追蹤脈絡，以追蹤識別碼串連一次執行。背景工作、重試及延後核對沿用業務操作識別碼。另起追蹤時，須能連回觸發操作或上游追蹤。外部識別碼須驗證格式與長度，只供關聯紀錄，不得充當授權依據或包含秘密與敏感資料。
- 應用程式、框架與 SDK 均須在寫出日誌、追蹤或稽核前選取必要欄位並遮蔽敏感資料，避免整包輸出請求或錯誤物件。密碼、權杖、工作階段 Cookie 與金鑰值在任何層級均禁止寫入。稽核確需記錄欄位值時，明訂用途、精度與存取範圍。保護要求見[安全共通規範](security.md#secrets-and-credentials)。

<a id="required-audit-events"></a>
## 必要稽核事件與內容

- 專案維護必要稽核事件清單，涵蓋安全規範要求可追溯的操作。逐項指定負責提供事實的模組、觸發條件，以及成功、拒絕或失敗時哪些結果須留存。例如拒絕申請人核准自己的申請，也可構成必要稽核事件。
- 每筆須能還原發生時間、操作者、操作、對象、適用資料範圍、當時授權依據與當時可確認的結果。代理、排程及覆核須區分發起者、執行身分與適用的核准人。使用可回查當時決策的參照，例如核准紀錄 ID。
- 非同步流程用操作識別碼串連各階段。退款已送出但金流結果未知時，記錄已知進度與待確認狀態，核對完成後追加實際結果。

<a id="audit-retention-and-access"></a>
## 保存保證、更正與查閱

- 需稽核的業務變更必須與稽核事實一起可靠保存，例如在同一交易提交變更與待送事件。無法可靠保存時，須在變更生效前停止。可靠保存後可非同步送往稽核平台，待送紀錄須可恢復且積壓可偵測。發布與重送要求見[事件可靠性](../interfaces/events.md#recoverable-publication)。
- 外部副作用已發生或結果未知時，保留已知事實、告警並指定後續核對責任。不得為補寫稽核而重做業務操作或宣稱已撤銷。
- 保存期間限制修改與刪除權限。一般業務服務只取得新增紀錄所需權限。更正採追加紀錄，連回原紀錄並記載更正人、時間、原因與依據。到期或依資料政策清除時，透過受控流程留下範圍、時間及執行依據。
- 查閱與匯出分別授權。單筆查閱也須限制事件類型、範圍與欄位。匯出須明訂用途、範圍及可下載期限，產物適用敏感資料副本政策。依風險追蹤敏感查閱與批量匯出，留下操作者、時間、用途或案件依據、資料範圍及結果，避免複製被查閱的內容。
- 各類紀錄依用途及敏感度明訂保存目的、期限起算點、可查閱期間與清除方式。封存資料須說明調閱條件與所需時間。查核期間須能取得必要授權依據、關聯及更正歷程。匯出檔、封存與備份依副本政策限制存取並到期清除。

<a id="metrics-and-freshness"></a>
## 指標與資料新鮮度

- 依業務承諾分別觀察受理、完成及未完成工作。受理階段可觀察請求量、技術錯誤率與耗時，並區分業務拒絕。完成率須明訂分子、分母與觀察窗口，避免把仍在期限內的新請求算成逾期。待辦須同時觀察積壓量與最舊未處理工作的等待時間。
- 每個指標明訂允許的標籤與值域。新增標籤時評估組合總量、成本與敏感資訊風險。單筆訂單、使用者或追蹤 ID、完整網址及原始錯誤文字不得直接作為指標標籤。單筆操作透過受控日誌與追蹤查找。
- 關鍵訊號須定義預期回報條件、容許延遲及失去觀測後的處置。週期訊號可依最後回報時間判定，低流量事件可搭配心跳或獨立訊號。佇列回報零筆與停止回報須可區分；資料過期標為過期或未知。若監控中斷影響及時發現問題的能力，須通知負責人。

<a id="alerting-and-resolution"></a>
## 告警與結案

- 依業務影響、持續時間及是否需在明確時限內採取行動決定告警。單筆日誌的嚴重程度不足以決定是否通知。
- 每條告警須定義受影響的業務承諾、門檻、觀察窗口、負責人或團隊、回應時限、第一個查核動作及解除條件。低流量流程也須能發現逾期的重要工作。
- 分別追蹤通知送達、有人接手與業務恢復。依嚴重程度設定接手期限，逾時無人確認時通知指定備援。同一事件集中更新；影響擴大或處置超時須升級。
- 達到恢復條件才結案。例如消費程序重啟後，仍須確認積壓回落且逾期退款已有結果或責任歸屬。停止重複通知或指標消失都不能自動解除事件。

<a id="sampling-and-pipeline-capacity"></a>
## 抽樣與管線容量

專案須指明可抽樣或丟棄的診斷資料、故障時優先保留的資訊，以及緩衝、重送的容量與時間上限。收集平台故障或滿載時依預定策略處理，必要稽核仍遵循可靠保存要求。讓查詢者可取得抽樣策略、有效抽樣率及可取得的丟棄數量或比例。由抽樣資料推算的指標須標示估算方式。

關鍵流程上線或觀測設定變更時，依影響範圍執行[可觀測性驗收](#acceptance)。

<a id="acceptance"></a>
## 驗收

驗收案例的選擇與維護依[驗收共同原則](testing.md#acceptance-principles)。

關鍵流程上線前，以及調整欄位、收集管線、告警路由或門檻後，須依風險在受控環境驗證受影響的流程。例如模擬退款已受理而背景工作停止處理，依日誌、稽核與可觀測性檢查下列結果。

- 從操作 ID 串回原請求及背景工作，能辨識最後完成的步驟。檢查實際寫出的紀錄，包含框架與 SDK 路徑，確認欄位正確且未寫出禁止的敏感資訊。
- 稽核可還原當時授權依據及已受理狀態。收集端離線後可恢復傳送，診斷抽樣不影響必要事件。業務恢復後追加核對結果，保留原始歷程。
- 確認積壓或等待時間超標時通知實際送達指定測試接收端，無人接手或影響擴大時會升級。停止回報須顯示未知，既有告警持續追蹤，直到業務恢復條件成立才解除。
