# 共通測試策略

## 層級與案例選擇

每項重要行為都須有對應測試。先辨識此次變更的承諾、受影響的使用端與失敗後果，再選擇能可靠驗證該行為且執行成本最低的層級。同一功能可讓不同層級各自驗證不同的保證。各主題已訂定的必測情境見[驗收入口](rule-verification.md#驗收入口)。

| 測試層級 | 以取消訂單為例，要驗證的行為 |
| --- | --- |
| 單元 | 已出貨訂單會拒絕取消，且維持原狀態。 |
| 整合 | 若訂單與庫存依設計共用交易，使用相容資料庫確認失敗時兩者均回滾。 |
| 契約 | 提供方依契約回報「已受理」，使用端正確解讀為仍待完成。 |
| 端對端 | 使用者送出取消後，能在訂單頁看見正確的最終狀態。 |

變更須驗證新行為、可能受影響的既有行為，以及應發生或應避免的副作用。若新增「已出貨不得取消」限制，須涵蓋遭拒的訂單、仍可取消的訂單，以及拒絕後是否誤發退款。修復缺陷時，使用能在修正前重現問題、修正後通過的迴歸案例；既有案例已能捕捉該缺陷時可以沿用。

## 斷言與替身

- 斷言對準可觀察的結果，包括回傳值、狀態變更及必要的外部互動。只有順序或次數會影響正確性時才加以限制，例如授權通過前不得發起扣款。私有方法的名稱與拆分方式可隨實作調整。
- 測試替身用來控制輸入與故障情境，須遵守被替代元件的公開契約，包括測試依賴的失敗語意。契約變更時一併核對替身及案例。
- 涉及相依元件本身的保證，須在相應整合路徑驗證。例如用替身回報金流逾時，可以驗證訂單進入待確認狀態。要驗證程式能辨識實際 SDK 的逾時錯誤，則須讓測試經過該 SDK。
- 測試替身無法證明的訊息或交易保證，必須以適當整合測試驗證。

## 案例獨立與穩定性

- 各案例自行建立或指定前置條件，單獨、調換順序或平行執行時，都應得到相同業務結果。唯讀基準資料可共用，可變資料與訊息須隔離。多步驟流程由同一案例負責前置條件及結果，斷言失敗時也須清理資源。
- 時間規則用可控制的時鐘驗證，涵蓋適用的時間邊界。非同步流程等待可觀察的完成條件並設定期限。逾時須保留操作識別、預期狀態及最後觀察結果，供追查。
- 同版程式在相同條件下間歇失敗時，保留首次失敗的斷言、資料識別、環境及適用的隨機種子或追蹤資訊。重跑可協助診斷，重跑通過仍須追查並修正程式、案例或環境的根因。
- 暫時將不穩定案例移出合併門檻，須由專案負責人核准，指定修復責任人、期限、恢復條件與期間的替代驗證方式。例外紀錄依[規範治理](../workflow/rule-governance.md)管理。

## 測試資料與環境

- 優先使用可重建的虛構資料，保留對結果有影響的特徵。例如驗證同時間建立的訂單能穩定分頁，可建立時間相同而 ID 不同的測試訂單。
- 正式環境衍生資料僅於必要且經專案核准時使用，須限縮擷取範圍、去識別化，並限制存取與保存期限。
- 資料庫、訊息佇列、付款及通知等目的地須使用隔離的測試資源與憑證，測試身分僅能操作指定資源。會產生副作用的測試在執行前須確認目的地，缺少必要設定或無法確認為測試環境時，停止並回報原因。
- 外部服務沒有沙箱時，可以受控替身驗證自己的流程，並在發布決策中列明仍待驗證的供應商行為。

## 執行門檻與驗收

專案依失敗後果與最晚可接受的發現時點，事先訂出各階段的必測項目與失敗處置。

| 階段 | 選擇與處置 |
| --- | --- |
| 合併前 | 驗證本次變更的核心行為與關鍵契約。需要整合測試才能證明的關鍵行為也在此階段驗證。必要項目失敗時阻擋合併。 |
| 發布前 | 在相容環境驗證實際組裝、設定及關鍵流程，必要項目失敗時阻擋發布。 |
| 定期執行 | 風險允許延後發現時，可安排長時間壓力測試或較廣的環境組合，須指定通知與處理責任。 |

驗收依據是關鍵行為有對應斷言。覆蓋率用於發現缺口，各專案可依模組風險訂門檻或追蹤變更部分的覆蓋率。只執行程式而未驗證可觀察結果的案例，不能作為該行為的驗收依據。

合併前的審查、必要檢查與核准有效性依[Git、PR 與程式碼審查](../workflow/git-pr-review.md)核對。

## 案例維護

已核准的行為變更須在同一次變更中更新受影響的契約、範例與測試，並保留仍受支援的舊行為驗證。若承諾仍有效，實作違反契約時修正實作；案例限制私有實作時，可改以公開結果驗證。

修改預期結果或移除案例時，審查須能確認理由，包括哪項承諾已變更或終止，或哪個既有案例仍能驗證同一風險。

### 可控制的併發驗收

併發與非同步流程須依風險，以可控制的交錯、完成條件及故障情境驗證正確性，不以固定睡眠或偶然成功作為主要證據。測試須有期限與診斷資訊，並搭配同步設計審查；壓力測試可補充驗證，但不能單獨證明執行緒安全。

## 驗收

### 補充契約驗收

依變更影響及實際採用能力選擇併發案例，測試層級與維護遵循本文件既有要求；不要求每個操作涵蓋全部情境，也不重測語言標準函式庫本身。

| 契約 | 驗收內容 |
| --- | --- |
| <a id="acceptance-controlled-interleaving"></a>[可控制的併發驗收](#controlled-interleaving) | 確認案例使用明確的協調與完成條件，等待有期限且失敗保留診斷資訊，涵蓋受影響的交錯與故障路徑。壓力測試結果須搭配同步及生命週期審查，不作為唯一安全證據。 |
